# ward-in-a-box

A simulated hospital ward as a load and chaos generator for health software.

## What it is

A pure Python 3 (stdlib only) simulator of a small ward — 12 beds by
default, each with a virtual monitor emitting vitals (heart rate, SpO2,
blood pressure, temperature, respiratory rate) at a configurable rate.
A chaos engine injects the failures real ward software has to survive:
device dropout, alarm storms, stale readings, and network partitions
between the ward and the server. An HTTP endpoint streams the vitals as
JSON lines so real health software can be tested against it, and a small
CLI runs a scenario file.

## What it is not

This is **not medical software**. It does not monitor real patients, it
does not diagnose or treat anything, and it must never be used in a
clinical setting. Every reading is synthetic, generated by a random
walk inside plausible ranges. It is a test tool for software, nothing
more.

## Quickstart

```sh
# Run the example scenario (12 beds, chaos starts at 30s)
python3 -m ward.cli scenarios/example.json

# Admissions ramp-up: 4 beds over 10s, then 8 by 50s, then all 12 by 70s
python3 -m ward.cli scenarios/ramp-up.json

# Ad-hoc ward: 6 beds at 2 Hz on port 9000
python3 -m ward.cli --beds 6 --rate 2 --port 9000

# Print one snapshot and exit
python3 -m ward.cli --beds 4 --once

# Record a run to a file, then summarise it (or replay its ticks)
python3 -m ward.cli scenarios/example.json --seed 42 --record run.jsonl
python3 -m ward.cli --summary run.jsonl
python3 -m ward.cli --replay run.jsonl

# Staffing demo: full day roster, one nurse on nights from 19:00
python3 -m ward.cli scenarios/staffing.json --seed 42

# Bed turnover: beds 1 and 2 discharge, clean for 10s, then refill
python3 -m ward.cli scenarios/turnover.json --seed 42

# Medication: interaction warnings up front, insulin missed on thin nights
python3 -m ward.cli scenarios/meds.json --seed 42

# Pharmacy stockout: insulin unavailable 5-3005 s, two doses skipped
python3 -m ward.cli scenarios/stockout.json --seed 42

# Triage intake: five patients queue up, two critical ones take beds
# 1 and 2 as they free up after discharge and cleaning
python3 -m ward.cli scenarios/triage.json --seed 42

# Wait-time alarms: a critical patient waiting 5 s and a low-acuity
# patient waiting 20 s both raise alarms while the ward stays full
python3 -m ward.cli scenarios/wait-alarm.json --seed 42

# Walk-in arrivals: quiet overnight, busy at midday, beds freeing
# up after discharge and cleaning
python3 -m ward.cli scenarios/arrivals.json --seed 42

# ED boarding: one patient queues, one boards in the ED, a third is
# diverted; the boarded patient takes the first freed bed
python3 -m ward.cli scenarios/boarding.json --seed 42

# Boarding-full alarm: boarding fills, two arrivals divert while it
# is full (one alarm episode, two diversions), the alarm clears when
# the boarded patient takes the bed freed at 15 s
python3 -m ward.cli scenarios/boarding-full.json --seed 42

# Discharge planning: three orders, one cleaning slot — two
# discharges wait for a slot and land 10 s and 8 s late
python3 -m ward.cli scenarios/discharge.json --seed 42

# Discharge readiness: one patient ready from 5 s, one once its
# dose lands at 30 s, one never (missed insulin), one in and out
# with a fever
python3 -m ward.cli scenarios/discharge-ready.json --seed 42

# Auto discharge orders: beds flagged ready get a discharge order
# raised for them at once, and discharge an hour later by default
python3 -m ward.cli scenarios/discharge-auto-order.json --seed 42

# Auto discharge orders with a 2 s lead-time override: the same
# beds discharge 2 s after flagging ready, not 5 s after
python3 -m ward.cli scenarios/discharge-auto-order-lead-time.json --seed 42

# Early warning: a hypoxic patient sits at medium NEWS2 risk, a
# febrile patient deteriorates on its own, and an alarm storm at
# 10 s pushes the febrile patient to high risk
python3 -m ward.cli scenarios/news2.json --seed 42

# Reproducible run
python3 -m ward.cli scenarios/example.json --seed 42
```

## Endpoints

- `GET /health` — `{"status": "ok", "beds": 12}`
- `GET /snapshot` — the latest reading for every bed as JSON,
  plus a `"staffing"` object (see below)
- `GET /stream` — the ward ticking live, one JSON object per line
- `GET /ws` — WebSocket endpoint streaming one JSON message per tick
  (beds plus alarm and staffing summaries; see below)
- `GET /alarms` — per-bed alarm history and rate metrics as JSON
  (503 while partitioned)
- `GET /staffing` — the current shift, roster on duty, nurse-to-patient
  ratio, alarm acknowledgement and vitals-check metrics as JSON
  (503 while partitioned)
- `GET /turnover` — per-bed turnover state (`occupied`, `cleaning`,
  `available`), turnovers and total cleaning time per bed, plus ward
  totals, as JSON (503 while partitioned)
- `GET /meds` — per-bed medication schedules, interaction warnings,
  and given/late/missed dose counts, plus ward totals, as JSON
  (503 while partitioned)
- `GET /triage` — the ED intake queue: waiting patients in priority
  order with acuity and wait so far, waiting counts per acuity,
  admitted/diverted totals, mean/max wait, and boarding-full alarm
  episodes, as JSON
  (503 while partitioned)
- `GET /arrivals` — the live arrivals view: current arrival rate,
  arrivals in the last hour of ward time, arrivals per ward clock
  hour so far, diversion status, and whether a boarding-full alarm
  is active, as JSON
  (503 while partitioned)
- `GET /discharge` — planned discharges: orders with their expected
  and actual discharge times, delays when cleaning was backed up,
  and the cleaning capacity and how many beds are cleaning or
  awaiting a slot, as JSON (503 while partitioned)
- `GET /discharge-readiness` — per-patient discharge-readiness
  flags (see below), as JSON (503 while partitioned)
- `GET /news2` — per-patient NEWS2 early-warning scores and
  deterioration episodes (see below), as JSON (503 while
  partitioned)

A reading looks like:

```json
{"bed": 2, "seq": 31, "t": 30.0, "profile": "tachycardic", "acuity": 2,
 "heart_rate": 108.4, "spo2": 96.2, "systolic": 128.0,
 "diastolic": 82.0, "temperature": 36.9, "resp_rate": 17.5,
 "alarms": [], "stale": false, "online": true}
```

Offline beds appear as `{"bed": 2, "online": false, "t": 30.0}`.
Beds not yet admitted by a scenario timeline appear the same way,
with an extra `"admitted": false`. While a partition is active,
`/snapshot` and `/stream` return 503.

## WebSocket endpoint

`GET /ws` with a standard WebSocket upgrade (`Upgrade: websocket`,
`Sec-WebSocket-Key`) returns `101 Switching Protocols` and then
streams one JSON text frame per tick at the ward rate:

```json
{"t": 30.0, "beds": [...], "alarms": {"t": 30.0, "beds": [...], "total_raised": 3, "rate_per_min": 1.2}, "staffing": {"t": 30.0, "shift": "day", "on_shift": {"nurse": 3, "doctor": 1, "tech": 1}, "patients_per_nurse": 4.0, "adequate": true, "alarms": {"raised": 3, "acked": 3, "pending": 0, "mean_time_to_ack_s": 30.0}, "checks": {"performed": 12, "delayed": 0}}}
```

Each frame carries the same snapshot as `/snapshot` plus the alarm
summary from `/alarms`, the staffing summary from `/staffing`, the
medication summary from `/meds`, the triage summary from
`/triage`, the live arrivals view from `/arrivals`, the
discharge summary from `/discharge`, the discharge-readiness
summary from `/discharge-readiness`, and the early-warning
summary from `/news2`, so a client gets bed occupancy, vitals, alarms, staffing,
medication, and the intake queue in one message. Ping frames are answered with pong, close frames
are echoed and the connection is then closed; text frames from the
client are accepted and ignored — the ward pushes ticks, it takes no
input. While a partition is active the upgrade is refused with 503,
like the other live endpoints. Pure stdlib: the framing is a minimal
hand-rolled RFC 6455 implementation in `ward/websocket.py`.

## Alarm history and rates

Every time a bed's vitals cross out of (or back into) a normal band, the
monitor records an alarm event:

```json
{"alarm": "tachycardia", "raised_t": 31.0, "cleared_t": 47.0}
```

`GET /alarms` returns, per bed, the alarms currently active, the full
history (capped at the last 1000 events per bed; the total count keeps
counting past the cap), the total number of alarms raised, and the alarm
rate — alarms raised per minute over a trailing 60-second window. The
ward totals are the sums across beds. A stale reading repeats the
previous alarms, so it records nothing; while a monitor is offline its
alarms are neither raised nor cleared, and transitions are recorded
against the last reading it emitted when it comes back.

## Scenario format

```json
{
  "beds": 12,
  "rate_hz": 1.0,
  "host": "127.0.0.1",
  "port": 8080,
  "patients": [{"bed": 0, "profile": "stable"}],
  "chaos": [
    {"type": "dropout", "bed": 2, "at": 30, "duration": 10},
    {"type": "stale", "bed": 5, "at": 45, "duration": 15},
    {"type": "alarm_storm", "beds": [0, 1, 2], "at": 60, "duration": 20},
    {"type": "partition", "at": 90, "duration": 15}
  ]
}
```

Patient profiles: `stable`, `tachycardic`, `hypoxic`, `febrile`.
Beds without a named profile cycle through a default mix.

## Patient acuity

Each patient also has an acuity, 1 (critical) to 4 (low/stable), on a
triage-like scale, set per patient in the scenario:

```json
{"bed": 0, "profile": "tachycardic", "acuity": 1}
```

Acuity changes how a patient's vitals behave. A critical patient
swings twice as hard per tick and wanders 35% further from the
profile midpoint, so they cross alarm bands more often; a low-acuity
patient is steadier and stays closer to the middle. Level 3 is the
neutral default and reproduces exactly the old profile behaviour, so
scenarios that do not set acuity are unchanged. Acuity 2 sits in
between (1.5x volatility, 15% wider). The widened ranges are clamped
inside a plausible envelope, so no acuity level can push a vital
somewhere a real monitor would never show. The reading and the
`/alarms` summary both carry the bed's acuity, so a client can tell a
quiet stable patient from a quiet critical one. See
`scenarios/acuity.json` for a ward with one patient at each level: over
a seeded 600-tick run the acuity-1 hypoxic patient raised 61 alarms
against 16 for the acuity-4 one.

Chaos types:

- `dropout` — a monitor goes offline for `duration` seconds; its bed
  stops appearing in the stream.
- `stale` — a monitor freezes on its last reading (flagged `"stale": true`).
- `alarm_storm` — vitals on the target beds are dragged out of their
  normal bands, so every bed raises alarms.
- `partition` — the ward is cut off from the server; endpoints return 503.
- `discharge` — the target beds' patients are discharged at `at`
  (instant, so `duration` is ignored and may be omitted); see
  Bed turnover below.
- `stockout` — the pharmacy runs out of a medication for `duration`
  seconds; needs `"med"`. Doses of that medication that fall due on
  the target beds while the stockout is active are skipped, recorded
  with status `stockout` in the dose history, counted in the
  medication metrics, and flagged with a `missed_dose` alarm; see
  Pharmacy stockouts below. Without `bed`/`beds` it applies to every
  bed that has the medication prescribed.

`bed` targets one bed, `beds` targets several, neither targets all beds
(`partition` is always ward-wide). Times are elapsed seconds from start.

## Staffing and shifts

The ward runs on two shifts — day 07:00–19:00, night 19:00–07:00 —
each with its own roster of nurses, doctors, and techs, set in the
scenario:

```json
{"staffing": {
  "start_hour": 18,
  "day": {"nurse": 3, "doctor": 1, "tech": 1},
  "night": {"nurse": 1, "doctor": 1, "tech": 0}
}}
```

The ward clock starts at `start_hour` (08:00 by default, an hour into
the day shift). What matters for care is the nurse-to-patient ratio:
one nurse keeps up with up to four occupied beds. Past that, alarms
take longer to acknowledge and routine vitals checks slip later, in
proportion to the overload. The first fifteen minutes after a shift
change are a handover, when response is half as fast again even with
a full roster. The model is deterministic: with an adequate roster an
alarm is acknowledged 30 seconds after it is raised and a vitals
check is due every 60 seconds; a ward with one nurse for twelve beds
acknowledges in 90 seconds and its checks run every 180 seconds, so
they count as delayed. `GET /staffing` (and every snapshot and
WebSocket frame) reports the shift, the roster on duty, the ratio,
whether it is adequate, the current load factor, alarms raised/acked/
pending with mean time-to-ack, and checks performed/delayed. See
`scenarios/staffing.json` for a ward that is fine on days and thin on
nights: over a seeded 400-tick alarm storm the full roster
acknowledged in 30.0 s on average with 0 delayed checks, against
90.0 s and 24 delayed checks with one nurse.

## Scenario timelines (admissions with ramp-up)

A scenario can add a `timeline` of admission phases. The ward starts
empty and beds come online as the timeline admits them — useful for
testing how health software handles a ward filling up, rather than a
ward that is full from the first second.

```json
{
  "beds": 12,
  "timeline": [
    {"at": 0, "beds": 4, "ramp_s": 10},
    {"at": 30, "beds": 8, "ramp_s": 20},
    {"at": 60, "beds": 12, "ramp_s": 10}
  ]
}
```

Each phase names a target number of occupied beds and a time to reach
it: starting at `at`, beds are admitted one by one over `ramp_s`
seconds until `beds` beds are occupied (`ramp_s` 0 admits them all at
once, at `at`). Between phases the occupancy stays at the last target.
Targets only go up — this is admissions, not discharges — and a phase
may not target more beds than the ward has. Beds keep the profiles
from the scenario's `patients` list (or the default mix) when they are
admitted. See `scenarios/ramp-up.json` for a runnable example.

## Bed turnover

When a patient is discharged, the bed is not free at once: it goes
through cleaning first. A bed has three states — `occupied` while a
patient is admitted, `cleaning` after a discharge until turnover
finishes, `available` once it can take a new admission. The cleaning
duration is `cleaning_s` seconds, set on the ward (30 by default) or
in the scenario:

```json
{
  "beds": 4,
  "cleaning_s": 10,
  "timeline": [{"at": 0, "beds": 4, "ramp_s": 0}],
  "chaos": [
    {"type": "discharge", "bed": 1, "at": 5},
    {"type": "discharge", "bed": 2, "at": 8}
  ]
}
```

A discharged bed stops emitting readings and cannot be re-admitted
until its cleaning time has elapsed — an admission attempt while
cleaning raises an error. A scenario timeline does not pull a bed out
of cleaning either: it refills the bed on the first tick after
turnover finishes, so a discharge followed by a refill tests exactly
the gap a real ward has. A new admission starts with fresh vitals, so
the previous patient's readings and alarms do not carry over, and a
discharge clears the patient's active alarms.

Every snapshot carries a `"turnover"` object with the per-bed state,
when a cleaning bed becomes available, how many turnovers each bed
has had, and the total cleaning time per bed, plus ward totals
(`occupied`, `cleaning`, `available`, `total_turnovers`,
`total_cleaning_s`). The same summary is served by `GET /turnover`.
Offline beds in a snapshot also carry their state (`"cleaning"` or
`"available"`). See `scenarios/turnover.json` for a runnable example:
bed 1 discharges at 5 s and is refilled at 15 s, bed 2 discharges at
8 s and is refilled at 18 s.

## Medication administration

Each patient can have scheduled medications, set per patient in the
scenario:

```json
{"bed": 0, "profile": "stable",
 "meds": [{"name": "metoprolol", "every_s": 3600,
           "first_at": 0, "grace_s": 600}]}
```

A dose due at `t` is administered 30 seconds later with a full
roster, slowed by the same staffing load factor that slows alarm
acknowledgement — so a thin night shift delays medication too. A dose
given more than 300 seconds after it was due counts as late; a dose
whose administration would land past `due + grace_s` (600 seconds by
default) is missed instead, and the miss raises a `missed_dose` alarm
on the bed until that medication's next dose is given. A discharge
clears the patient's medication state, and a new admission starts
with a fresh schedule.

Some medication pairs interact. A small table of known pairs
(warfarin + aspirin, metoprolol + verapamil, insulin + metoprolol,
lisinopril + spironolactone, digoxin + furosemide) produces warnings
in the medication summary — warnings only, the doses still happen,
because a simulator should surface the risk, not decide the
prescription.

Every snapshot carries a `"meds"` object with the per-bed schedules,
warnings, given/late/missed counts, and ward totals. The same
summary is served by `GET /meds`. See `scenarios/meds.json` for a
runnable example: bed 0 is on warfarin and aspirin, bed 1 on
time-critical insulin with a 60-second grace window, bed 3 on
lisinopril and spironolactone. Over a seeded 7200-tick run the day
shift gives every dose, the night shift (one nurse for twelve beds)
misses the insulin dose, and 2 interaction warnings are raised.

## Pharmacy stockouts

A `stockout` chaos event makes one medication unavailable for a
window:

```json
{"type": "stockout", "med": "insulin", "bed": 1, "at": 5, "duration": 3000}
```

A dose of that medication that falls due while the stockout is active
is skipped at once — it is never queued for administration. The
skipped dose is recorded in the dose history with status `stockout`
(`admin_t` null), counted separately in the per-bed dose counts and
the ward `total_stockout`, and it raises a `missed_dose` alarm on the
bed until that medication's next dose is given, exactly like a dose
missed for staffing reasons. The per-bed summary also lists the
medications currently stocked out (`"stockouts"`), so a client can
tell a skipped dose from a staffing miss. Doses already pending when
the stockout starts still resolve normally; only doses that fall due
inside the window are skipped. See `scenarios/stockout.json` for a
runnable example: over a seeded 3700-tick run the insulin doses due
at 1200 s and 2400 s are skipped while the pharmacy is out, the
doses due at 0 s and 3600 s are given, and the metoprolol on the
other bed is unaffected.

## Triage / ED intake queue

Patients arrive at triage with an acuity and wait in an intake queue
until a bed frees up. Arrivals are scheduled in the scenario:

```json
{
  "beds": 4,
  "triage": {
    "capacity": 5,
    "arrivals": [
      {"at": 0, "acuity": 1, "profile": "hypoxic"},
      {"at": 2, "acuity": 3, "profile": "stable"}
    ]
  }
}
```

When a bed becomes available — a discharge followed by its cleaning
— the highest-priority waiting patient is admitted: lowest acuity
number first (1 is critical), earliest arrival first within an
acuity, so a critical patient who arrives later still jumps the
queue. The new admission starts with fresh vitals at that patient's
acuity and profile. If the queue is full when a patient arrives, the
patient is diverted (counted, not queued). A bed the scenario
timeline has not admitted yet is reserved for the timeline: triage
only takes beds that have freed up through a discharge. Patients can
also be added live with `ward.triage_arrive(acuity, profile)`.

Every snapshot carries a `"triage"` object with the waiting patients
in priority order (acuity, profile, arrival time, wait so far),
waiting counts per acuity, the queue capacity, admitted and diverted
totals, mean and max wait of admitted patients, and the longest
current wait. The same summary is served by `GET /triage`. See
`scenarios/triage.json` for a runnable example: five patients queue
while the ward is full, beds 1 and 2 discharge at 5 s and 8 s, and
the two critical patients are admitted at 15 s and 18 s once
cleaning finishes, after waiting 15 s and 9 s.

## Triage wait-time alarms

A patient who waits too long raises an alarm. Each acuity has its
own wait threshold — 300 s for acuity 1, 900 s for acuity 2, 1800 s
for acuity 3, 3600 s for acuity 4, the same shape as real ED triage
targets — set per scenario with `wait_thresholds`:

```json
{"triage": {"capacity": 5, "wait_thresholds": {"1": 300, "4": 3600}}}
```

The alarm raises at exactly `arrival_t + threshold`, once, and
clears when the patient is admitted. Each waiting patient in the
triage summary carries their threshold, whether their alarm is
raised, and when it raised; the summary also lists the thresholds,
the total alarms raised, how many are currently active, and the
full alarm history with raised and cleared times. See
`scenarios/wait-alarm.json` for a runnable example: over a seeded
25-tick run the critical patient raises an alarm at 5 s and the
low-acuity patient at 22 s while the ward stays full.

## Walk-in / Poisson arrivals

Scheduled arrivals are not how an ED works: walk-ins show up at
random, at a rate that rises and falls through the day. A scenario
can add a `poisson` arrival model to its `triage` block instead of
(or alongside) scheduled arrivals:

```json
{"triage": {
  "capacity": 5,
  "poisson": {
    "hourly_rates": [30, 30, 30, 30, 30, 30, 60, 90, 180, 180, 180,
                     180, 150, 150, 150, 150, 150, 120, 120, 90, 90,
                     90, 60, 60]
  }
}}
```

Each tick draws a Poisson count with mean `rate * dt` — the rate
read at the ward clock hour, so the ward is quiet overnight and
busy at midday — and each arrival draws an acuity and a profile
from configurable weights (defaults: mostly acuity 3-4, half
stable). A flat rate works too: `"poisson": {"rate_per_hour": 120}`.
The draws come from the ward's seeded RNG, so `--seed 42` reproduces
exactly the same arrivals. Walk-ins join the same triage queue as
scheduled arrivals: they wait for a bed freed by discharge and
cleaning, or are diverted when the queue is full. The triage
summary carries the current arrival rate
(`arrival_rate_per_hour`), the hourly rate table, and how many
walk-ins have been generated (`arrivals_generated`); it also
carries arrivals per ward clock hour (`arrivals_by_hour`), so the
ED load shape over the day is visible — every arrival counts
toward its hour, whether it joined the queue or was diverted
when the queue was full, and the per-hour counts add up to the
total arrivals. The run summary (`--summary`) reports the same
per-hour arrivals alongside the configured hourly rates. See
`scenarios/arrivals.json` for a runnable example: over a
seeded 60-tick run at 180/hr, 3 walk-ins arrive, 2 take the beds
freed by the discharges at 5 s and 8 s, and 1 is still waiting.

## Live arrivals view

The triage summary already carries the arrival rate and the
per-hour counts, but a dashboard wants the live picture in one
place. Every snapshot carries an `"arrivals"` object, served on its
own by `GET /arrivals` and included in every WebSocket frame:

```json
{"t": 600.0, "arrival_rate_per_hour": 180.0, "arrivals_last_hour": 178,
 "arrivals_total": 178, "arrivals_by_hour": {"8": 178},
 "waiting_total": 3, "capacity": 8, "boarding_total": 0,
 "boarding_capacity": 0, "boarded": 0, "admitted": 2, "diverted": 0,
 "diverted_last_hour": 0, "diverting": false,
 "boarding_full_alarm": false, "boarding_full_alarms_raised": 0}
```

`arrival_rate_per_hour` is the walk-in rate at the current ward
clock hour (null with no Poisson model — scheduled arrivals still
count). `arrivals_last_hour` counts arrivals in the trailing hour
of ward time, `(now - 3600, now]`, so it slides forward as the ward
runs; `arrivals_total` counts every patient who showed up, whether
they joined the queue or were diverted. `diverting` is true while
the queue is full and boarding is full too, so new arrivals are
being turned away, with `diverted` and `diverted_last_hour`
counting them; `boarding_total`, `boarding_capacity`, and
`boarded` say how many patients are boarding now, how many
boarding spots the ED has, and how many have boarded in total
(see ED boarding below). Over a seeded 60-tick run of
`scenarios/arrivals.json` the view reports 3 arrivals in the last
hour, all in hour 8, matching the triage summary.

## ED boarding (overflow)

When the intake queue is full, a patient is not always diverted: if
the scenario sets a `boarding_capacity` on its `triage` block, the
patient boards instead — they wait in the ED for an inpatient bed,
up to that many boarded patients at once. Boarding is off by
default (`boarding_capacity` 0), so scenarios that do not set it
behave exactly as before.

```json
{"triage": {"capacity": 1, "boarding_capacity": 1, "arrivals": [...]}}
```

A boarded patient is already admitted to the hospital, so when a
bed frees up they take it before a patient still waiting in the
intake queue — within each group the usual triage priority applies
(lowest acuity first, earliest arrival first). Boarded patients
raise the same wait-time alarms as queued ones, marked
`"boarding": true` in the wait-alarm history, and their waits are
tracked separately (`mean_boarding_wait_s`, `max_boarding_wait_s`,
`longest_boarding_wait_s`). The triage summary lists the boarded
patients, the boarding total and capacity, and how many have
boarded in total; the live arrivals view carries the same counts,
and `diverting` is true only when the queue and boarding are both
full. See `scenarios/boarding.json` for a runnable example: over a
seeded run three patients arrive while the ward is full — one
queues, one boards, the critical third is diverted — and the
boarded patient takes the bed freed at 15 s after waiting 14 s,
while the queued patient takes the bed freed at 18 s after
waiting 18 s.

Limitation: boarding is an overflow buffer, not a second ward.
Boarded patients get no vitals, no medication schedules, and no
bedside monitor until they are admitted to a bed — the model only
tracks that they are waiting, how long, and whether they raised a
wait-time alarm.

## Boarding-full alarm

When boarding is full and a new arrival is diverted because both
the intake queue and boarding are full, a boarding-full alarm
raises: the ED is turning patients away for lack of anywhere to
put them. One alarm episode covers one continuous full period —
it raises at the first diversion while boarding is full, further
diversions during the episode count against it instead of raising
a second alarm, and it clears when a boarded patient is admitted
to a bed and a boarding spot frees up. A diversion with boarding
off (`boarding_capacity` 0) raises nothing: with no boarding to
fill, it is a plain diversion, not a boarding failure.

The triage summary carries the episodes (`boarding_full_alarms_raised`,
`boarding_full_alarm_active`, `boarding_full_alarm_history` with
`raised_t`, `cleared_t`, and how many patients were diverted during
each episode, and the `boarding_full_diverted` total), the live
arrivals view carries whether one is active
(`boarding_full_alarm`) and how many have raised, and the run
summary (`--summary`) reports the same totals from the last tick.
See `scenarios/boarding-full.json` for a runnable example: over a
seeded 20-tick run boarding fills at 1 s, two arrivals divert at
2 s and 3 s inside a single episode, the boarded patient takes the
bed freed at 15 s and the alarm clears, and the queued patient
takes the bed freed at 18 s.

## Discharge planning

A discharge is not instant in a real ward: the doctor orders it in
the morning and the patient leaves hours later, and the bed only
frees up once cleaning finishes. A scenario can plan discharges
with a lead time:

```json
{
  "beds": 4,
  "cleaning_s": 10,
  "cleaning_capacity": 1,
  "discharge_planning": {
    "lead_time_s": 5,
    "orders": [
      {"bed": 0, "at": 0},
      {"bed": 1, "at": 0},
      {"bed": 2, "at": 12}
    ]
  }
}
```

Each order names a bed and when it is placed; the patient is
discharged at `at + lead_time_s` (the planner's default lead time,
an hour by default, when an order does not set its own). The bed
then goes through cleaning as usual, so a planned discharge
followed by a triage admission tests exactly the gap between the
order and the bed being free. An order for a bed whose patient
already left — a chaos `discharge` event fired first — is
cancelled, not forced. Orders can also be placed live with
`ward.discharge_planner.place_order(bed, now)`.

`cleaning_capacity` caps how many beds can be cleaned at once
(unlimited by default, so existing scenarios behave exactly as
before). When every slot is busy, a discharge is delayed: the
patient stays in the bed, still monitored and still emitting
vitals, until a slot frees up, and the delay is recorded — on the
order, in the per-bed turnover totals, and in the ward totals.
Every snapshot carries a `"discharge"` object with the orders
(bed, ordered, expected, and actual times, status, delay, and
where the order came from — `"source"`: `"manual"`, `"scheduled"`,
or `"auto"`), how many were planned, discharged, delayed, and
cancelled, and the total and mean delay, plus the cleaning capacity,
how many beds are cleaning, and how many are awaiting a slot. The same
summary is served by `GET /discharge` and carried in every
WebSocket frame, and the run summary (`--summary`) reports the
discharge totals. See `scenarios/discharge.json` for a runnable
example: over a seeded 40-tick run with one cleaning slot, all
three planned discharges land, two of them late — bed 1 by 10 s
and bed 2 by 8 s, 18 s of delay in total.

## Discharge readiness

A patient is flagged discharge-ready when their vitals have been
stable for a configurable window and all their orders are
complete. Stable means no alarm raised in the window, measured from
the last time their alarms cleared (or from admission, if they
never alarmed) — an alarm storm restarts the clock. Orders means
medication orders: no dose still waiting to be given, and no missed
dose that has not been followed by a given one; a patient with no
medications has nothing outstanding. A planned discharge order does
not block readiness — a patient whose discharge is already ordered
is exactly the patient this flag is for. The flag is advisory only:
this is a test tool, not a clinical judgement.

```json
{
  "beds": 4,
  "discharge_readiness": {"stable_window_s": 300}
}
```

The window is 300 seconds by default. Every reading carries a
`"discharge_ready"` flag, every snapshot carries a
`"discharge_readiness"` object with the per-patient flags (ready,
admitted, seconds stable, the window in force, orders complete)
and ward totals, served on its own by `GET /discharge-readiness`
and carried in every WebSocket frame, and the run summary
(`--summary`) reports the same totals from the last tick. See
`scenarios/discharge-ready.json` for a runnable example: over a
seeded 40-tick run with a 5-second window, bed 0 (stable, no
orders) flags ready from 5 s, bed 1 (one metoprolol dose, given
at 30 s) from 30 s, bed 2 (insulin missed at 1 s on a 1-second
grace window) never flags ready, and bed 3 (febrile, alarms
coming and going) flags ready at 40 s after 6 s of quiet vitals —
3 ready, 1 not.

With `"auto_order": true` in the `discharge_readiness` block the
ward acts on the flag: the first tick a bed is flagged ready, it
raises a discharge-planning order for that bed (marked
`"source": "auto"` in the discharge summary, counted as
`auto_planned`), so the patient is discharged `lead_time_s`
later through the normal planning flow — including the cleaning
backlog, so a backed-up roster delays an auto discharge like
any other. One order per stay: a bed with a live order already
in flight (planned or delayed, manual, scheduled, or auto) gets
no second one, and a new patient admitted to the bed later gets
a fresh order of their own. The per-bed readiness detail carries
`"auto_ordered"` while such an order is live, and the run
summary reports `auto_planned` alongside the discharge totals.
Off by default, so wards that do not ask for it behave exactly
as before. See `scenarios/discharge-auto-order.json` for a
runnable example: over a seeded 40-tick run with a 5-second
window and a 5-second lead time, beds 0 and 3 are quiet from
admission and auto-discharge at 10 s, bed 1's dose lands at 30 s
and it auto-discharges at 35 s, and bed 2 (missed insulin) never
flags ready and gets no order — 3 auto orders, 3 discharges.

## Discharge paperwork timing

The discharge summary also measures how long the paperwork takes:
for each order, `ready_t` is when its bed was first flagged
discharge-ready in the current stay, `ready_to_order_s` is the
time from that flag to the order being placed, and
`ready_to_discharge_s` is the time from the flag to the patient
actually leaving — so it includes any delay waiting for a
cleaning slot. An order placed before its bed was ready has no
ready-to-order time (the order was already in flight when the
patient became ready), and an order for a bed that never flagged
ready has no timing at all. The summary aggregates the measured
orders as `"timing"` — how many were measured, the mean
ready-to-order and ready-to-discharge times, and the longest
ready-to-discharge time — so a ward can see whether the
paperwork or the cleaning roster is what holds a bed up. The
timing rides along with the discharge summary everywhere it
goes: every snapshot, WebSocket frame, `GET /discharge`, and
the run summary (`--summary`). See
`scenarios/discharge-auto-order.json` for a runnable example:
over a seeded 40-tick run every order is placed the tick its bed
flags ready and every patient leaves 5 s after flagging, so the
timing reports 3 measured orders, a mean ready-to-order time of
0.0 s, and a mean and max ready-to-discharge time of 5.0 s.

## Per-auto-order lead-time override

Auto orders normally use the planner's default lead time, but a
ward that sends a ready patient home quickly can override it for
auto orders only, with `auto_order_lead_time_s` in the
`discharge_readiness` block:

```json
{
  "discharge_planning": {"lead_time_s": 3600},
  "discharge_readiness": {
    "auto_order": true,
    "auto_order_lead_time_s": 600,
    "stable_window_s": 300
  }
}
```

The override applies only to orders the ward raises itself when a
bed is flagged discharge-ready. Scheduled orders still use the
planner's default (or their own per-order `lead_time_s`), and
manual orders placed live with `place_order` take whatever lead
time they are given. The discharge summary's orders already carry
each order's `expected_t`, so the override is visible there; the
readiness summary carries the override in force
(`auto_order_lead_time_s`, null when unset) in every snapshot,
WebSocket frame, `GET /discharge-readiness`, and the run summary
(`--summary`). See `scenarios/discharge-auto-order-lead-time.json`
for a runnable example: over a seeded 40-tick run with a 5-second
window, a 5-second planner default, and a 2-second override, beds
0 and 3 are quiet from admission and auto-discharge at 7 s, bed
1's dose lands at 30 s and it auto-discharges at 32 s, and bed 2
(missed insulin) never flags ready and gets no order — 3 auto
orders, 3 discharges, a mean ready-to-discharge time of 2.0 s.

## NEWS2 early-warning scoring

Every reading carries a NEWS2 score — the Royal College of
Physicians' National Early Warning Score 2 — computed from that
tick's vitals:

```json
{"news2": {"score": 6, "risk": "medium", "red_score": true,
 "components": {"resp_rate": 2, "spo2": 3, "systolic": 0,
 "heart_rate": 1, "temperature": 0},
 "response": "urgent review by ward team (hourly monitoring)"}}
```

Each of the five scored parameters contributes 0 to 3 points on
the standard NEWS2 bands (respiratory rate, SpO2 on Scale 1,
systolic blood pressure, heart rate, temperature). The aggregate
drives the risk: 0-4 low, 5-6 medium, 7 or more high — and any
single parameter scoring 3 is a red score, which makes the risk
medium even when the aggregate is low. The response is NEWS2's
own: routine monitoring at low risk, urgent review by the ward
team at medium, urgent review by the critical care team at high.

Two honest limitations. Consciousness (ACVPU) is not scored: the
simulator generates no consciousness state, so a ward score is a
partial NEWS2, missing one of its six parameters. And SpO2 uses
Scale 1 only, because the ward has no oxygen-therapy state for
Scale 2 to apply to. The score is advisory only — a test signal
for health software, not a clinical judgement.

A patient whose risk leaves low opens a deterioration episode:
it records when it raised, the worst score it reached, and the
worst risk, and it closes when the risk returns to low (or when
the patient is discharged). Every snapshot carries an
`"early_warning"` object with the per-bed scores, whether an
episode is open, the episode history, and ward totals (beds at
each risk level, open episodes, episodes raised), served on its
own by `GET /news2` and carried in every WebSocket frame, and
the run summary (`--summary`) reports the same totals from the
last tick. The score never touches the alarm list: a hypoxic
patient's alarms are exactly the ones their vitals raise, so
alarm counts, alarm rates, and discharge readiness are
unchanged. See `scenarios/news2.json` for a runnable example:
over a seeded 40-tick run the stable bed scores 0 and never
escalates, the hypoxic bed sits at medium risk on a red SpO2
score and stays escalated from 1 s, the tachycardic bed stays
low, and the febrile bed deteriorates on its own (a medium
episode at 5-9 s) and then goes high under the alarm storm at
10 s, peaking at 11 and clearing at 40 s — 3 episodes raised in
total.

## Recording a run

`--record FILE` writes every tick to a JSONL file: a header line with
the run's beds, rate, and seed, then one line per tick holding the
snapshot exactly as the ward emitted it. Plain JSONL, so any tool can
read a recording without this package.

```sh
python3 -m ward.cli --summary run.jsonl   # ticks, duration, readings/offline/stale per bed, alarms raised
python3 -m ward.cli --replay run.jsonl    # the recorded ticks, one JSON object per line
```

The summary counts an alarm once, when it first appears in a bed's
reading — the same raise/clear transitions the monitor records. A
recording with a partition in it still records every tick; the
endpoints returned 503 while it lasted, the ticks did not stop.
