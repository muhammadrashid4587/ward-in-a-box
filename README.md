# ward-in-a-box

A simulated hospital ward as a load and chaos generator for health software.

## What it is

A pure Python 3 (stdlib only) simulator of a small ward — 12 beds by
default, each with a virtual monitor emitting vitals (heart rate, SpO2,
blood pressure, temperature, respiratory rate) at a configurable rate.
A chaos engine injects the failures real ward software has to survive:
device dropout, alarm storms, stale readings, and network partitions
between the ward and the server. An HTTP endpoint streams the vitals as
JSON lines so real health software can be tested against it, and a small
CLI runs a scenario file.

## What it is not

This is **not medical software**. It does not monitor real patients, it
does not diagnose or treat anything, and it must never be used in a
clinical setting. Every reading is synthetic, generated by a random
walk inside plausible ranges. It is a test tool for software, nothing
more.

## Endpoints

- `GET /health` — `{"status": "ok", "beds": 12}`
- `GET /snapshot` — the latest reading for every bed as JSON,
  plus a `"staffing"` object (see below)
- `GET /stream` — the ward ticking live, one JSON object per line
- `GET /ws` — WebSocket endpoint streaming one JSON message per tick
  (beds plus alarm and staffing summaries; see below)
- `GET /alarms` — per-bed alarm history and rate metrics as JSON
  (503 while partitioned)
- `GET /staffing` — the current shift, roster on duty, nurse-to-patient
  ratio, alarm acknowledgement and vitals-check metrics as JSON
  (503 while partitioned)
- `GET /turnover` — per-bed turnover state (`occupied`, `cleaning`,
  `available`), turnovers and total cleaning time per bed, plus ward
  totals, as JSON (503 while partitioned)
- `GET /meds` — per-bed medication schedules, interaction warnings,
  and given/late/missed dose counts, plus ward totals and
  missed-dose hook totals, as JSON
  (503 while partitioned)
- `GET /triage` — the ED intake queue: waiting patients in priority
  order with acuity and wait so far, waiting counts per acuity,
  admitted/diverted totals, mean/max wait, and boarding-full alarm
  episodes, as JSON
  (503 while partitioned)
- `GET /arrivals` — the live arrivals view: current arrival rate,
  arrivals in the last hour of ward time, arrivals per ward clock
  hour so far, diversion status, and whether a boarding-full alarm
  is active, as JSON
  (503 while partitioned)
- `GET /discharge` — planned discharges: orders with their expected
  and actual discharge times, delays when cleaning was backed up,
  and the cleaning capacity and how many beds are cleaning or
  awaiting a slot, as JSON (503 while partitioned)
- `GET /discharge-readiness` — per-patient discharge-readiness
  flags (see below), as JSON (503 while partitioned)
- `GET /discharge-priority` — discharge-ready beds ranked by
  NEWS2, safest first, plus the order-change history and the
  discharge-priority hook totals (see below), as JSON (503 while
  partitioned)
- `GET /news2` — per-patient NEWS2 early-warning scores and
  deterioration episodes (see below), as JSON (503 while
  partitioned)
- `GET /news2/history` — per-patient NEWS2 score history: every
  score this stay, one entry per reading, with the peak score and
  risk, the latest score, and the current trend and trend alerts
  (see below); `?bed=N` returns one bed
  (404 for a bed the ward does not have, 400 for a bed that is not
  an integer), as JSON (503 while partitioned)
- `GET /sensor-drift` — per-bed sensor-drift state: the accumulated
  bias per vital on each bed, how many beds have a drifted sensor,
  and the largest absolute bias per vital, as JSON
  (503 while partitioned)
- `GET /bed-blocker` — per-bed bed-blocker state: whether each bed
  is blocked, why, and when the block ends, how many beds are
  blocked, and how many discharges are held by a block, as JSON
  (503 while partitioned)
- `GET /oxygen-outage` — per-bed oxygen-outage state: whether the
  supply is down, when it returns, and how many SpO2 points each
  patient on oxygen has lost to it, as JSON
  (503 while partitioned)

A reading looks like:

```json
{"bed": 2, "seq": 31, "t": 30.0, "profile": "tachycardic", "acuity": 2,
 "heart_rate": 108.4, "spo2": 96.2, "systolic": 128.0,
 "diastolic": 82.0, "temperature": 36.9, "resp_rate": 17.5,
 "alarms": [], "stale": false, "online": true}
```

Offline beds appear as `{"bed": 2, "online": false, "t": 30.0}`.
Beds not yet admitted by a scenario timeline appear the same way,
with an extra `"admitted": false`. While a partition is active,
`/snapshot` and `/stream` return 503.

## WebSocket endpoint

`GET /ws` with a standard WebSocket upgrade (`Upgrade: websocket`,
`Sec-WebSocket-Key`) returns `101 Switching Protocols` and then
streams one JSON text frame per tick at the ward rate:

```json
{"t": 30.0, "beds": [...], "alarms": {"t": 30.0, "beds": [...], "total_raised": 3, "rate_per_min": 1.2}, "staffing": {"t": 30.0, "shift": "day", "on_shift": {"nurse": 3, "doctor": 1, "tech": 1}, "patients_per_nurse": 4.0, "adequate": true, "alarms": {"raised": 3, "acked": 3, "pending": 0, "mean_time_to_ack_s": 30.0}, "checks": {"performed": 12, "delayed": 0}}}
```

Each frame carries the same snapshot as `/snapshot` plus the alarm
summary from `/alarms`, the staffing summary from `/staffing`, the
medication summary from `/meds`, the triage summary from
`/triage`, the live arrivals view from `/arrivals`, the
discharge summary from `/discharge`, the discharge-readiness
summary from `/discharge-readiness`, the discharge-priority
summary from `/discharge-priority`, the early-warning
summary from `/news2`, and the sensor-drift summary from
`/sensor-drift`, the bed-blocker summary from
`/bed-blocker`, and the oxygen-outage summary from
`/oxygen-outage`, so a client gets bed occupancy, vitals, alarms, staffing,
medication, and the intake queue in one message. Ping frames are answered with pong, close frames
are echoed and the connection is then closed; text frames from the
client are accepted and ignored — the ward pushes ticks, it takes no
input. While a partition is active the upgrade is refused with 503,
like the other live endpoints. Pure stdlib: the framing is a minimal
hand-rolled RFC 6455 implementation in `ward/websocket.py`.

## Alarm history and rates

Every time a bed's vitals cross out of (or back into) a normal band, the
monitor records an alarm event:

```json
{"alarm": "tachycardia", "raised_t": 31.0, "cleared_t": 47.0}
```

`GET /alarms` returns, per bed, the alarms currently active, the full
history (capped at the last 1000 events per bed; the total count keeps
counting past the cap), the total number of alarms raised, and the alarm
rate — alarms raised per minute over a trailing 60-second window. The
ward totals are the sums across beds. A stale reading repeats the
previous alarms, so it records nothing; while a monitor is offline its
alarms are neither raised nor cleared, and transitions are recorded
against the last reading it emitted when it comes back.

## Scenario format

```json
{
  "beds": 12,
  "rate_hz": 1.0,
  "host": "127.0.0.1",
  "port": 8080,
  "patients": [{"bed": 0, "profile": "stable"}],
  "chaos": [
    {"type": "dropout", "bed": 2, "at": 30, "duration": 10},
    {"type": "stale", "bed": 5, "at": 45, "duration": 15},
    {"type": "alarm_storm", "beds": [0, 1, 2], "at": 60, "duration": 20},
    {"type": "partition", "at": 90, "duration": 15}
  ]
}
```

Patient profiles: `stable`, `tachycardic`, `hypoxic`, `febrile`.
Beds without a named profile cycle through a default mix.

## Patient acuity

Each patient also has an acuity, 1 (critical) to 4 (low/stable), on a
triage-like scale, set per patient in the scenario:

```json
{"bed": 0, "profile": "tachycardic", "acuity": 1}
```

Acuity changes how a patient's vitals behave. A critical patient
swings twice as hard per tick and wanders 35% further from the
profile midpoint, so they cross alarm bands more often; a low-acuity
patient is steadier and stays closer to the middle. Level 3 is the
neutral default and reproduces exactly the old profile behaviour, so
scenarios that do not set acuity are unchanged. Acuity 2 sits in
between (1.5x volatility, 15% wider). The widened ranges are clamped
inside a plausible envelope, so no acuity level can push a vital
somewhere a real monitor would never show. The reading and the
`/alarms` summary both carry the bed's acuity, so a client can tell a
quiet stable patient from a quiet critical one. See
`scenarios/acuity.json` for a ward with one patient at each level: over
a seeded 600-tick run the acuity-1 hypoxic patient raised 61 alarms
against 16 for the acuity-4 one.

Chaos types:

- `dropout` — a monitor goes offline for `duration` seconds; its bed
  stops appearing in the stream.
- `stale` — a monitor freezes on its last reading (flagged `"stale": true`).
- `alarm_storm` — vitals on the target beds are dragged out of their
  normal bands, so every bed raises alarms.
- `partition` — the ward is cut off from the server; endpoints return 503.
- `discharge` — the target beds' patients are discharged at `at`
  (instant, so `duration` is ignored and may be omitted); see
  Bed turnover below.
- `stockout` — the pharmacy runs out of a medication for `duration`
  seconds; needs `"med"`. Doses of that medication that fall due on
  the target beds while the stockout is active are skipped, recorded
  with status `stockout` in the dose history, counted in the
  medication metrics, and flagged with a `missed_dose` alarm; see
  Pharmacy stockouts below. Without `bed`/`beds` it applies to every
  bed that has the medication prescribed.
- `sensor_drift` — a bed's sensor slowly miscalibrates for `duration`
  seconds; needs `"drift"`, a map of vital to drift rate per second
  (for example `{"spo2": -0.15, "heart_rate": 0.5}`). While the event
  is active the bias grows by `rate * dt` every tick, so the reported
  reading creeps away from the patient's true vitals instead of
  jumping — a ramp, not a step. The bias stays once the event ends
  (a drifted sensor does not heal itself) and is cleared only when a
  new patient is admitted to the bed; see Slow sensor drift below.
- `staff_shortage` — staff call in sick for `duration` seconds;
  needs `"shortage"`, a map of staff role to how many of that
  role are lost (for example `{"nurse": 1}`). While it is active
  the lost staff are off the effective roster, so the
  nurse-to-patient ratio rises and alarms take longer to
  acknowledge and vitals checks slip, exactly as a thin roster
  would; ward-wide, so `bed`/`beds` are ignored. Only lost
  nurses change the modelled care — a lost doctor or tech is
  recorded but slows nothing; see Staff shortage below.
- `bed_blocker` — a bed is out of use for `duration` seconds;
  needs `"reason"`, one of `"porter"`, `"isolation_clean"`, or
  `"equipment_fault"`. While it is active the bed cannot take a
  new admission and its patient cannot be discharged until the
  block clears; a discharge attempted while blocked is held and
  goes through the moment the block ends, with the wait recorded
  as a discharge delay; see Bed blocker below.
- `oxygen_outage` — the ward's oxygen supply fails for `duration`
  seconds; needs `"oxygen"`, a map with `"rate"` (SpO2 points lost
  per second, required), `"floor"` (the lowest SpO2 the outage can
  push a patient to, default 82.0), and `"recovery_rate"` (points
  regained per second once the supply returns, default the fall
  rate). While it is active a patient on oxygen really desaturates
  — the low_spo2 alarm, the NEWS2 score, trend alerts, and
  escalations all respond — while a patient not on oxygen is
  untouched, because the outage is a supply failure and only the
  patients the supply was feeding feel it; see Oxygen outage below.

`bed` targets one bed, `beds` targets several, neither targets all beds
(`partition` is always ward-wide). Times are elapsed seconds from start.

## Staffing and shifts

The ward runs on two shifts — day 07:00–19:00, night 19:00–07:00 —
each with its own roster of nurses, doctors, and techs, set in the
scenario:

```json
{"staffing": {
  "start_hour": 18,
  "day": {"nurse": 3, "doctor": 1, "tech": 1},
  "night": {"nurse": 1, "doctor": 1, "tech": 0}
}}
```

The ward clock starts at `start_hour` (08:00 by default, an hour into
the day shift). What matters for care is the nurse-to-patient ratio:
one nurse keeps up with up to four occupied beds. Past that, alarms
take longer to acknowledge and routine vitals checks slip later, in
proportion to the overload. The first fifteen minutes after a shift
change are a handover, when response is half as fast again even with
a full roster. The model is deterministic: with an adequate roster an
alarm is acknowledged 30 seconds after it is raised and a vitals
check is due every 60 seconds; a ward with one nurse for twelve beds
acknowledges in 90 seconds and its checks run every 180 seconds, so
they count as delayed. `GET /staffing` (and every snapshot and
WebSocket frame) reports the shift, the roster on duty, the ratio,
whether it is adequate, the current load factor, alarms raised/acked/
pending with mean time-to-ack, and checks performed/delayed. See
`scenarios/staffing.json` for a ward that is fine on days and thin on
nights: over a seeded 400-tick alarm storm the full roster
acknowledged in 30.0 s on average with 0 delayed checks, against
90.0 s and 24 delayed checks with one nurse.

## Scenario timelines (admissions with ramp-up)

A scenario can add a `timeline` of admission phases. The ward starts
empty and beds come online as the timeline admits them — useful for
testing how health software handles a ward filling up, rather than a
ward that is full from the first second.

```json
{
  "beds": 12,
  "timeline": [
    {"at": 0, "beds": 4, "ramp_s": 10},
    {"at": 30, "beds": 8, "ramp_s": 20},
    {"at": 60, "beds": 12, "ramp_s": 10}
  ]
}
```

Each phase names a target number of occupied beds and a time to reach
it: starting at `at`, beds are admitted one by one over `ramp_s`
seconds until `beds` beds are occupied (`ramp_s` 0 admits them all at
once, at `at`). Between phases the occupancy stays at the last target.
Targets only go up — this is admissions, not discharges — and a phase
may not target more beds than the ward has. Beds keep the profiles
from the scenario's `patients` list (or the default mix) when they are
admitted. See `scenarios/ramp-up.json` for a runnable example.

## Bed turnover

When a patient is discharged, the bed is not free at once: it goes
through cleaning first. A bed has three states — `occupied` while a
patient is admitted, `cleaning` after a discharge until turnover
finishes, `available` once it can take a new admission — plus a
fourth, `blocked`, while a bed-blocker event holds a bed that has
finished cleaning (see Bed blocker below). The cleaning
duration is `cleaning_s` seconds, set on the ward (30 by default) or
in the scenario:

```json
{
  "beds": 4,
  "cleaning_s": 10,
  "timeline": [{"at": 0, "beds": 4, "ramp_s": 0}],
  "chaos": [
    {"type": "discharge", "bed": 1, "at": 5},
    {"type": "discharge", "bed": 2, "at": 8}
  ]
}
```

A discharged bed stops emitting readings and cannot be re-admitted
until its cleaning time has elapsed — an admission attempt while
cleaning raises an error. A scenario timeline does not pull a bed out
of cleaning either: it refills the bed on the first tick after
turnover finishes, so a discharge followed by a refill tests exactly
the gap a real ward has. A new admission starts with fresh vitals, so
the previous patient's readings and alarms do not carry over, and a
discharge clears the patient's active alarms.

Every snapshot carries a `"turnover"` object with the per-bed state,
when a cleaning bed becomes available, how many turnovers each bed
has had, and the total cleaning time per bed, plus ward totals
(`occupied`, `cleaning`, `available`, `total_turnovers`,
`total_cleaning_s`). The same summary is served by `GET /turnover`.
Offline beds in a snapshot also carry their state (`"cleaning"` or
`"available"`). See `scenarios/turnover.json` for a runnable example:
bed 1 discharges at 5 s and is refilled at 15 s, bed 2 discharges at
8 s and is refilled at 18 s.

## Medication administration

Each patient can have scheduled medications, set per patient in the
scenario:

```json
{"bed": 0, "profile": "stable",
 "meds": [{"name": "metoprolol", "every_s": 3600,
           "first_at": 0, "grace_s": 600}]}
```

A dose due at `t` is administered 30 seconds later with a full
roster, slowed by the same staffing load factor that slows alarm
acknowledgement — so a thin night shift delays medication too. A dose
given more than 300 seconds after it was due counts as late; a dose
whose administration would land past `due + grace_s` (600 seconds by
default) is missed instead, and the miss raises a `missed_dose` alarm
on the bed until that medication's next dose is given. A discharge
clears the patient's medication state, and a new admission starts
with a fresh schedule.

Some medication pairs interact. A small table of known pairs
(warfarin + aspirin, metoprolol + verapamil, insulin + metoprolol,
lisinopril + spironolactone, digoxin + furosemide) produces warnings
in the medication summary — warnings only, the doses still happen,
because a simulator should surface the risk, not decide the
prescription.

Every snapshot carries a `"meds"` object with the per-bed schedules,
warnings, given/late/missed counts, and ward totals. The same
summary is served by `GET /meds`. See `scenarios/meds.json` for a
runnable example: bed 0 is on warfarin and aspirin, bed 1 on
time-critical insulin with a 60-second grace window, bed 3 on
lisinopril and spironolactone. Over a seeded 7200-tick run the day
shift gives every dose, the night shift (one nurse for twelve beds)
misses the insulin dose, and 2 interaction warnings are raised.

## Pharmacy stockouts

A `stockout` chaos event makes one medication unavailable for a
window:

```json
{"type": "stockout", "med": "insulin", "bed": 1, "at": 5, "duration": 3000}
```

A dose of that medication that falls due while the stockout is active
is skipped at once — it is never queued for administration. The
skipped dose is recorded in the dose history with status `stockout`
(`admin_t` null), counted separately in the per-bed dose counts and
the ward `total_stockout`, and it raises a `missed_dose` alarm on the
bed until that medication's next dose is given, exactly like a dose
missed for staffing reasons. The per-bed summary also lists the
medications currently stocked out (`"stockouts"`), so a client can
tell a skipped dose from a staffing miss. Doses already pending when
the stockout starts still resolve normally; only doses that fall due
inside the window are skipped. See `scenarios/stockout.json` for a
runnable example: over a seeded 3700-tick run the insulin doses due
at 1200 s and 2400 s are skipped while the pharmacy is out, the
doses due at 0 s and 3600 s are given, and the metoprolol on the
other bed is unaffected.

## Slow sensor drift

A `sensor_drift` chaos event makes one or more beds' sensors
slowly miscalibrate:

```json
{"type": "sensor_drift", "bed": 0, "at": 5, "duration": 60,
 "drift": {"spo2": -0.15, "heart_rate": 0.5}}
```

While the event is active, each target bed's bias for those vitals
grows by `rate * dt` every tick — SpO2 reading 0.15 lower every
second, heart rate 0.5 higher — so the reported reading creeps
away from the patient's true vitals. The bias is a property of
the sensor, not the patient: the monitor's stored vitals stay
true, and only the reading it reports — and the alarms and NEWS2
score computed from it — see the drift. A runaway drift saturates
at the edge of the plausible envelope (SpO2 never reports above
100, heart rate never below 30), so the ward never shows a reading
a real monitor could not. The bias persists after the event ends,
and a new admission recalibrates the sensor, so a fresh patient
starts clean — though a still-active drift event starts drifting
them again from zero on the next tick.

The point is the creep: a step change trips alarms at once, but a
drift makes the NEWS2 score climb one point at a time and flips
discharge-readiness off only when the reported vitals finally cross
a band — the failure mode a ward's early-warning and discharge
software has to catch gradually, not at once. Every reading
carries its bed's current bias (`"sensor_drift"`, empty while the
sensor is clean), every snapshot carries a `"sensor_drift"` object
with the per-bed biases, how many beds are drifting, and the
largest absolute bias per vital, served on its own by
`GET /sensor-drift` and carried in every WebSocket frame, and the
run summary (`--summary`) reports the same totals from the last
tick. See `scenarios/sensor-drift.json` for a runnable example:
over a seeded 70-tick run bed 0's SpO2 bias reaches -9.0 and its
heart-rate bias +30.0, its NEWS2 creeps 0, 1, 2, 4, 5 to medium
risk, a `low_spo2` alarm raises at 47 s, and it stops being
discharge-ready on the same tick after flagging ready at 5 s,
while bed 1 stays at NEWS2 0.

## Staff shortage

A `staff_shortage` chaos event takes staff off the effective
roster for a window — a nurse calling in sick mid-shift:

```json
{"type": "staff_shortage", "at": 10, "duration": 30,
 "shortage": {"nurse": 1}}
```

While the event is active, that many staff are gone: the
nurse-to-patient ratio rises and care slows exactly as a thin
roster would — alarms take longer to acknowledge, routine
vitals checks slip later, and medication doses land later,
all through the same load factor the staffing model already
uses. When the window ends the roster is whole again and the
load factor drops straight back. Overlapping shortage events
add up, so two sick calls for one nurse each lose two nurses,
and losing the whole roster leaves the ward with no nurse at
all (load factor 4.0). The staffing summary carries the
current shortage (`"shortage"`, empty when the roster is
whole) alongside the rostered staff and the escalation
nurses, in every snapshot, WebSocket frame, `GET /staffing`,
and the run summary (`--summary`). Only lost nurses change
the modelled care: a lost doctor or tech is recorded in the
summary but slows nothing, because the model keys response
times off nurses alone. See `scenarios/staff-shortage.json`
for a runnable example: over a seeded 70-tick run one nurse
is out from 10 s to 40 s during an alarm storm on beds 0-2,
the load factor sits at 1.5 for the window and 1.0 either
side of it, and all 15 storm alarms are acknowledged in
45.0 s on average instead of 30.0 s.

## Bed blocker

A `bed_blocker` chaos event takes a bed out of use for a window —
a bed awaiting a porter to move its patient, an isolation clean
after an infectious patient, or an equipment fault on the bed
itself:

```json
{"type": "bed_blocker", "bed": 1, "at": 5, "duration": 20,
 "reason": "porter"}
```

While the event is active, the bed cannot take a new admission —
a scenario timeline will not admit to it, the triage queue skips
it even when it has finished cleaning, and a live admission is
refused — and its patient cannot be discharged: a discharge
attempted while blocked, whether a chaos `discharge` event or a
planned discharge order due inside the window, is held, and goes
through on the very tick the block ends. The wait is recorded as
a discharge delay, exactly like a discharge held behind a full
cleaning roster, so the delay shows up in the per-bed turnover
totals, the discharge summary, and the run summary. A blocked
bed that has finished cleaning reports state `"blocked"` in the
turnover summary instead of `"available"`, so a client can tell
a bed that is free from one that is free but unusable. Every
snapshot carries a `"bed_blocker"` object with the per-bed block
state — whether it is blocked, why, and when the block ends —
and whether a discharge is still waiting on it, plus ward totals
(how many beds are blocked, how many discharges are held, and
how many the run has held), served on its own by
`GET /bed-blocker` and carried in every WebSocket frame, and the
run summary (`--summary`) reports the same totals from the last
tick. See `scenarios/bed-blocker.json` for a runnable example:
over a seeded 40-tick run bed 1 waits for a porter from 5 s to
25 s, so its discharge at 10 s is held until 25 s (15 s late),
and bed 3 finishes cleaning at 15 s but is blocked for an
isolation clean until 30 s, so the waiting triage patient takes
bed 2 when it frees at 20 s instead, after waiting 20 s.

## Oxygen outage

An `oxygen_outage` chaos event fails the ward's oxygen supply for a
window — a manifold fault, an empty bulk tank, a cut line — so the
patients on oxygen lose the gas that was keeping them saturated:

```json
{"type": "oxygen_outage", "at": 5, "duration": 30,
 "oxygen": {"rate": 0.5, "floor": 82.0, "recovery_rate": 1.0}}
```

While the event is active, a patient on oxygen loses `rate` SpO2
points every second, down to `floor`, and recovers at
`recovery_rate` points a second once the supply returns. The fall
is a real desaturation, not a sensor error: unlike `sensor_drift`,
which lies about the reading while the patient is fine, the outage
moves the patient's true SpO2, so the low_spo2 alarm raises, the
NEWS2 score climbs, trend alerts fire, and deterioration episodes
open exactly as they would for a patient genuinely deteriorating —
and a bed stops being discharge-ready while it is desaturating. A
patient not on oxygen is untouched: they have no supply to lose,
so the same event leaves them at NEWS2 0 while their neighbour
falls. Without `bed`/`beds` the outage is ward-wide, like a
partition: the supply serves the whole ward. The deficit is
deterministic — pure arithmetic on the tick, no RNG — so a seeded
run reproduces it exactly, and a new admission starts fully
saturated (an outage still running starts desaturating them again
from zero). Every reading carries its bed's current deficit as
`"oxygen_deficit"`, every snapshot carries an `"oxygen_outage"`
object with the per-bed outage state — whether the supply is down,
when it returns, and how many SpO2 points each patient has lost —
and ward totals (how many patients are on oxygen, how many are
desaturating, and the largest loss), served on its own by
`GET /oxygen-outage` and carried in every WebSocket frame, and the
run summary (`--summary`) reports the same totals from the last
tick. See `scenarios/oxygen-outage.json` for a runnable example:
over a seeded 70-tick run bed 0 (stable, on oxygen) falls from
SpO2 95 to 82.95 as its deficit ramps to 13.84, raises a low_spo2
alarm at 19 s, peaks at NEWS2 4 (medium), and is fully recovered
by 50 s; bed 2 (hypoxic, on oxygen) sits on the 82.0 floor from
21 s with NEWS2 6 (medium); bed 1 (stable, not on oxygen) is
untouched by the outage — its deficit stays 0.0 throughout.

## Triage / ED intake queue

Patients arrive at triage with an acuity and wait in an intake queue
until a bed frees up. Arrivals are scheduled in the scenario:

```json
{
  "beds": 4,
  "triage": {
    "capacity": 5,
    "arrivals": [
      {"at": 0, "acuity": 1, "profile": "hypoxic"},
      {"at": 2, "acuity": 3, "profile": "stable"}
    ]
  }
}
```

When a bed becomes available — a discharge followed by its cleaning
— the highest-priority waiting patient is admitted: lowest acuity
number first (1 is critical), earliest arrival first within an
acuity, so a critical patient who arrives later still jumps the
queue. The new admission starts with fresh vitals at that patient's
acuity and profile. If the queue is full when a patient arrives, the
patient is diverted (counted, not queued). A bed the scenario
timeline has not admitted yet is reserved for the timeline: triage
only takes beds that have freed up through a discharge. Patients can
also be added live with `ward.triage_arrive(acuity, profile)`.

Every snapshot carries a `"triage"` object with the waiting patients
in priority order (acuity, profile, arrival time, wait so far),
waiting counts per acuity, the queue capacity, admitted and diverted
totals, mean and max wait of admitted patients, and the longest
current wait. The same summary is served by `GET /triage`. See
`scenarios/triage.json` for a runnable example: five patients queue
while the ward is full, beds 1 and 2 discharge at 5 s and 8 s, and
the two critical patients are admitted at 15 s and 18 s once
cleaning finishes, after waiting 15 s and 9 s.

## Triage wait-time alarms

A patient who waits too long raises an alarm. Each acuity has its
own wait threshold — 300 s for acuity 1, 900 s for acuity 2, 1800 s
for acuity 3, 3600 s for acuity 4, the same shape as real ED triage
targets — set per scenario with `wait_thresholds`:

```json
{"triage": {"capacity": 5, "wait_thresholds": {"1": 300, "4": 3600}}}
```

The alarm raises at exactly `arrival_t + threshold`, once, and
clears when the patient is admitted. Each waiting patient in the
triage summary carries their threshold, whether their alarm is
raised, and when it raised; the summary also lists the thresholds,
the total alarms raised, how many are currently active, and the
full alarm history with raised and cleared times. See
`scenarios/wait-alarm.json` for a runnable example: over a seeded
25-tick run the critical patient raises an alarm at 5 s and the
low-acuity patient at 22 s while the ward stays full.

## Walk-in / Poisson arrivals

Scheduled arrivals are not how an ED works: walk-ins show up at
random, at a rate that rises and falls through the day. A scenario
can add a `poisson` arrival model to its `triage` block instead of
(or alongside) scheduled arrivals:

```json
{"triage": {
  "capacity": 5,
  "poisson": {
    "hourly_rates": [30, 30, 30, 30, 30, 30, 60, 90, 180, 180, 180,
                     180, 150, 150, 150, 150, 150, 120, 120, 90, 90,
                     90, 60, 60]
  }
}}
```

Each tick draws a Poisson count with mean `rate * dt` — the rate
read at the ward clock hour, so the ward is quiet overnight and
busy at midday — and each arrival draws an acuity and a profile
from configurable weights (defaults: mostly acuity 3-4, half
stable). A flat rate works too: `"poisson": {"rate_per_hour": 120}`.
A ramp works instead of either: `"poisson": {"ramp":
{"from_per_hour": 30, "to_per_hour": 180, "over_s": 600}}` rises
linearly from 30/hr at `at` (0 by default) to 180/hr 600 s later,
so an ED load builds up over a shift instead of switching on —
`over_s` 0 steps the rate at `at` instead. The ramp reads elapsed
time, not the ward clock hour, and like the flat and hourly rates
it is mutually exclusive with them: give exactly one of
`rate_per_hour`, `hourly_rates`, or `ramp`.
The draws come from the ward's seeded RNG, so `--seed 42` reproduces
exactly the same arrivals. Walk-ins join the same triage queue as
scheduled arrivals: they wait for a bed freed by discharge and
cleaning, or are diverted when the queue is full. The triage
summary carries the current arrival rate
(`arrival_rate_per_hour`), the hourly rate table, and how many
walk-ins have been generated (`arrivals_generated`); when a ramp
is configured it carries the ramp instead (`arrival_ramp`, with
`at`, `from_per_hour`, `to_per_hour`, and `over_s`), and the run
summary (`--summary`) reports the same ramp config alongside the
rate at the last tick. The triage summary also
carries arrivals per ward clock hour (`arrivals_by_hour`), so the
ED load shape over the day is visible — every arrival counts
toward its hour, whether it joined the queue or was diverted
when the queue was full, and the per-hour counts add up to the
total arrivals. The run summary (`--summary`) reports the same
per-hour arrivals alongside the configured hourly rates. See
`scenarios/arrivals.json` for a runnable example: over a
seeded 60-tick run at 180/hr, 3 walk-ins arrive, 2 take the beds
freed by the discharges at 5 s and 8 s, and 1 is still waiting.
See `scenarios/arrival-ramp.json` for the same ward with a ramp
instead of a flat table: over a seeded 60-tick run the rate rises
from 60/hr to 1800/hr, 11 walk-ins arrive, 2 take the beds freed
by the discharges at 5 s and 8 s, 4 are diverted, and 5 are still
waiting.

## Live arrivals view

The triage summary already carries the arrival rate and the
per-hour counts, but a dashboard wants the live picture in one
place. Every snapshot carries an `"arrivals"` object, served on its
own by `GET /arrivals` and included in every WebSocket frame:

```json
{"t": 600.0, "arrival_rate_per_hour": 180.0, "arrivals_last_hour": 178,
 "arrivals_total": 178, "arrivals_by_hour": {"8": 178},
 "waiting_total": 3, "capacity": 8, "boarding_total": 0,
 "boarding_capacity": 0, "boarded": 0, "admitted": 2, "diverted": 0,
 "diverted_last_hour": 0, "diverting": false,
 "boarding_full_alarm": false, "boarding_full_alarms_raised": 0}
```

`arrival_rate_per_hour` is the walk-in rate at the current ward
clock hour (null with no Poisson model — scheduled arrivals still
count). `arrivals_last_hour` counts arrivals in the trailing hour
of ward time, `(now - 3600, now]`, so it slides forward as the ward
runs; `arrivals_total` counts every patient who showed up, whether
they joined the queue or were diverted. `diverting` is true while
the queue is full and boarding is full too, so new arrivals are
being turned away, with `diverted` and `diverted_last_hour`
counting them; `boarding_total`, `boarding_capacity`, and
`boarded` say how many patients are boarding now, how many
boarding spots the ED has, and how many have boarded in total
(see ED boarding below). Over a seeded 60-tick run of
`scenarios/arrivals.json` the view reports 3 arrivals in the last
hour, all in hour 8, matching the triage summary.

## ED boarding (overflow)

When the intake queue is full, a patient is not always diverted: if
the scenario sets a `boarding_capacity` on its `triage` block, the
patient boards instead — they wait in the ED for an inpatient bed,
up to that many boarded patients at once. Boarding is off by
default (`boarding_capacity` 0), so scenarios that do not set it
behave exactly as before.

```json
{"triage": {"capacity": 1, "boarding_capacity": 1, "arrivals": [...]}}
```

A boarded patient is already admitted to the hospital, so when a
bed frees up they take it before a patient still waiting in the
intake queue — within each group the usual triage priority applies
(lowest acuity first, earliest arrival first). Boarded patients
raise the same wait-time alarms as queued ones, marked
`"boarding": true` in the wait-alarm history, and their waits are
tracked separately (`mean_boarding_wait_s`, `max_boarding_wait_s`,
`longest_boarding_wait_s`). The triage summary lists the boarded
patients, the boarding total and capacity, and how many have
boarded in total; the live arrivals view carries the same counts,
and `diverting` is true only when the queue and boarding are both
full. See `scenarios/boarding.json` for a runnable example: over a
seeded run three patients arrive while the ward is full — one
queues, one boards, the critical third is diverted — and the
boarded patient takes the bed freed at 15 s after waiting 14 s,
while the queued patient takes the bed freed at 18 s after
waiting 18 s.

Limitation: boarding is an overflow buffer, not a second ward.
Boarded patients get no vitals, no medication schedules, and no
bedside monitor until they are admitted to a bed — the model only
tracks that they are waiting, how long, and whether they raised a
wait-time alarm.

## Boarding-full alarm

When boarding is full and a new arrival is diverted because both
the intake queue and boarding are full, a boarding-full alarm
raises: the ED is turning patients away for lack of anywhere to
put them. One alarm episode covers one continuous full period —
it raises at the first diversion while boarding is full, further
diversions during the episode count against it instead of raising
a second alarm, and it clears when a boarded patient is admitted
to a bed and a boarding spot frees up. A diversion with boarding
off (`boarding_capacity` 0) raises nothing: with no boarding to
fill, it is a plain diversion, not a boarding failure.

The triage summary carries the episodes (`boarding_full_alarms_raised`,
`boarding_full_alarm_active`, `boarding_full_alarm_history` with
`raised_t`, `cleared_t`, and how many patients were diverted during
each episode, and the `boarding_full_diverted` total), the live
arrivals view carries whether one is active
(`boarding_full_alarm`) and how many have raised, and the run
summary (`--summary`) reports the same totals from the last tick.
See `scenarios/boarding-full.json` for a runnable example: over a
seeded 20-tick run boarding fills at 1 s, two arrivals divert at
2 s and 3 s inside a single episode, the boarded patient takes the
bed freed at 15 s and the alarm clears, and the queued patient
takes the bed freed at 18 s.

## Boarding-full alarm hooks

A boarding-full alarm says the ED is turning patients away for lack
of anywhere to put them; the hook makes sure something outside the
ward hears about it. A ward that wants the outside world to hear
about that moment — a pager, a dashboard, a bed manager — configures
boarding-full hooks, the same channels as the NEWS2 hooks (webhook
and/or in-process callback), on the same best-effort, never-fatal
terms:

```json
{"boarding_full_hooks": {"webhook_url": "http://127.0.0.1:18099/hooks"}}
```

The hook fires once, in the tick the boarding-full alarm episode
raises, with a `boarding_full_alarm` event payload: when it raised,
how many patients were diverted during the episode so far, and when
it cleared (null while it is active). The episode records whether
the hook was invoked (`"hook_invoked"`, False with no hooks) and any
synchronous error (`"hook_errors"`), and the triage summary carries
the ward boarding-full-hook totals (`"boarding_full_hooks"`: whether
any hook is configured, how many deliveries were invoked, how many
failed, how many retries were spent, and how many deliveries
eventually landed) — in `GET /triage`, every snapshot and WebSocket
frame, and the run summary (`--summary`). The same retry rules as
the NEWS2 hooks apply — a failed webhook POST is retried with
backoff up to `"max_retries"` times, and the episode records
`"hook_retries"` and `"hook_final_status"` alongside
`"hook_invoked"`. Further diversions during the episode fire
nothing: one episode, one notification. Hooks are off by default,
so a ward with none configured behaves exactly as before. See
`scenarios/boarding-full-hooks.json` for a runnable example: over a
seeded 20-tick run the same 1 boarding-full episode raises as in
`boarding-full.json`, POSTed to the configured webhook, with 1 hook
delivery invoked and 0 failed against a stub server.

## Wait-time alarm hooks

A wait-time alarm says a patient has waited too long for a bed; the

one alarm, one notification. Hooks are off by default, so a ward

## Missed-dose hooks

A missed dose says a patient did not get a medication they were
due — because the ward was too thin to give it inside its grace
window, or because the pharmacy was out of it; the hook makes sure
something outside the ward hears about it. A ward that wants the
outside world to hear about that moment — a pager, a dashboard, a
pharmacist — configures missed-dose hooks, the same channels as
the NEWS2 hooks (webhook and/or in-process callback), on the same
best-effort, never-fatal terms:

```json
{"missed_dose_hooks": {"webhook_url": "http://127.0.0.1:18099/hooks"}}
```

The hook fires once per missed dose, in the tick the miss is
recorded, with a `missed_dose` event payload: the bed, the
medication, when the dose was due, when it was missed, and why —
`"reason": "staffing"` when the grace window expired before the
ward could give it, `"stockout"` when the pharmacy was out of
that medication. The dose's history entry records whether the
hook was invoked (`"hook_invoked"`, False with no hooks) and any
synchronous error (`"hook_errors"`), and the medication summary
carries the ward missed-dose-hook totals
(`"missed_dose_hooks"`: whether any hook is configured, how many
deliveries were invoked, how many failed, how many retries were
spent, and how many deliveries eventually landed) — in
`GET /meds`, every snapshot and WebSocket frame, and the run
summary (`--summary`). The same retry rules as the NEWS2 hooks
apply — a failed webhook POST is retried with backoff up to
`"max_retries"` times, and the entry records `"hook_retries"`
and `"hook_final_status"` alongside `"hook_invoked"`. A dose
given on time fires nothing: only a miss reaches the outside
world. Hooks are off by default, so a ward with none configured
behaves exactly as before. See
`scenarios/missed-dose-hooks.json` for a runnable example: over a
seeded 3650-tick run with no nurse on shift the insulin dose due
at 0 s is missed at 60 s and the dose due at 3600 s is skipped
while the pharmacy is out, POSTed to the configured webhook, with
2 hook deliveries invoked and 0 failed against a stub server.

## Discharge planning

A discharge is not instant in a real ward: the doctor orders it in
the morning and the patient leaves hours later, and the bed only
frees up once cleaning finishes. A scenario can plan discharges
with a lead time:

```json
{
  "beds": 4,
  "cleaning_s": 10,
  "cleaning_capacity": 1,
  "discharge_planning": {
    "lead_time_s": 5,
    "orders": [
      {"bed": 0, "at": 0},
      {"bed": 1, "at": 0},
      {"bed": 2, "at": 12}
    ]
  }
}
```

Each order names a bed and when it is placed; the patient is
discharged at `at + lead_time_s` (the planner's default lead time,
an hour by default, when an order does not set its own). The bed
then goes through cleaning as usual, so a planned discharge
followed by a triage admission tests exactly the gap between the
order and the bed being free. An order for a bed whose patient
already left — a chaos `discharge` event fired first — is
cancelled, not forced. Orders can also be placed live with
`ward.discharge_planner.place_order(bed, now)`.

`cleaning_capacity` caps how many beds can be cleaned at once
(unlimited by default, so existing scenarios behave exactly as
before). When every slot is busy, a discharge is delayed: the
patient stays in the bed, still monitored and still emitting
vitals, until a slot frees up, and the delay is recorded — on the
order, in the per-bed turnover totals, and in the ward totals.
Every snapshot carries a `"discharge"` object with the orders
(bed, ordered, expected, and actual times, status, delay, where
the order came from — `"source"`: `"manual"`, `"scheduled"`,
or `"auto"` — and, for a cancelled order, when it was withdrawn
and why, `cancelled_t` and `cancel_reason`), how many were
planned, discharged, delayed, and cancelled, and the total and
mean delay, plus the cleaning capacity,
how many beds are cleaning, and how many are awaiting a slot,
in the order cleaning will start them (`cleaning_queue`,
discharge-priority order, safest first). The same
summary is served by `GET /discharge` and carried in every
WebSocket frame, and the run summary (`--summary`) reports the
discharge totals. See `scenarios/discharge.json` for a runnable
example: over a seeded 40-tick run with one cleaning slot, all
three planned discharges land, two of them late — bed 1 by 10 s
and bed 2 by 8 s, 18 s of delay in total.

## Discharge readiness

A patient is flagged discharge-ready when their vitals have been
stable for a configurable window and all their orders are
complete. Stable means no alarm raised in the window, measured from
the last time their alarms cleared (or from admission, if they
never alarmed) — an alarm storm restarts the clock. Orders means
medication orders: no dose still waiting to be given, and no missed
dose that has not been followed by a given one; a patient with no
medications has nothing outstanding. A planned discharge order does
not block readiness — a patient whose discharge is already ordered
is exactly the patient this flag is for. The flag is advisory only:
this is a test tool, not a clinical judgement.

```json
{
  "beds": 4,
  "discharge_readiness": {"stable_window_s": 300}
}
```

The window is 300 seconds by default. Every reading carries a
`"discharge_ready"` flag, every snapshot carries a
`"discharge_readiness"` object with the per-patient flags (ready,
admitted, seconds stable, the window in force, orders complete)
and ward totals, served on its own by `GET /discharge-readiness`
and carried in every WebSocket frame, and the run summary
(`--summary`) reports the same totals from the last tick. See
`scenarios/discharge-ready.json` for a runnable example: over a
seeded 40-tick run with a 5-second window, bed 0 (stable, no
orders) flags ready from 5 s, bed 1 (one metoprolol dose, given
at 30 s) from 30 s, bed 2 (insulin missed at 1 s on a 1-second
grace window) never flags ready, and bed 3 (febrile, alarms
coming and going) flags ready at 40 s after 6 s of quiet vitals —
3 ready, 1 not.

With `"auto_order": true` in the `discharge_readiness` block the
ward acts on the flag: the first tick a bed is flagged ready, it
raises a discharge-planning order for that bed (marked
`"source": "auto"` in the discharge summary, counted as
`auto_planned`), so the patient is discharged `lead_time_s`
later through the normal planning flow — including the cleaning
backlog, so a backed-up roster delays an auto discharge like
any other. One order per stay: a bed with a live order already
in flight (planned or delayed, manual, scheduled, or auto) gets
no second one, and a new patient admitted to the bed later gets
a fresh order of their own. An auto order is the ward's own call,
so it is withdrawn when the reason for it goes away: the first
tick its bed stops being discharge-ready — an alarm restarted
the stability clock, or a dose became outstanding — a live auto
order is cancelled (stamped with when and why, `cancelled_t`
and `cancel_reason` `"not_ready"`, counted as `auto_cancelled`),
and the bed gets a fresh auto order when it flags ready again.
Manual and scheduled orders are never cancelled this way: they
are a doctor's order, not the ward's. The per-bed readiness detail carries
`"auto_ordered"` while such an order is live, and the run
summary reports `auto_planned` alongside the discharge totals.
Off by default, so wards that do not ask for it behave exactly
as before. See `scenarios/discharge-auto-order.json` for a
runnable example: over a seeded 40-tick run with a 5-second
window and a 5-second lead time, bed 0 is quiet from admission
and auto-discharges at 10 s, bed 3 flags ready at 5 s but alarms
at 8 s, so its auto order is cancelled and it never leaves, bed
1's dose lands at 30 s and it auto-discharges at 35 s, and bed 2
(missed insulin) never flags ready and gets no order — 3 auto
orders, 2 discharges, 1 cancelled. See
`scenarios/discharge-auto-order-cancel.json` for the
cancellation-and-fresh-order case: the same ward with an alarm
storm on bed 0 at 6 s, whose first alarm at 7 s cancels bed 0's
order, and a fresh auto order at 16 s discharges it at 21 s —
4 auto orders, 3 discharges, 1 cancelled.

## Discharge paperwork timing

The discharge summary also measures how long the paperwork takes:
for each order, `ready_t` is when its bed was first flagged
discharge-ready in the current stay, `ready_to_order_s` is the
time from that flag to the order being placed, and
`ready_to_discharge_s` is the time from the flag to the patient
actually leaving — so it includes any delay waiting for a
cleaning slot. An order placed before its bed was ready has no
ready-to-order time (the order was already in flight when the
patient became ready), and an order for a bed that never flagged
ready has no timing at all. The summary aggregates the measured
orders as `"timing"` — how many were measured, the mean
ready-to-order and ready-to-discharge times, and the longest
ready-to-discharge time — so a ward can see whether the
paperwork or the cleaning roster is what holds a bed up. The
timing rides along with the discharge summary everywhere it
goes: every snapshot, WebSocket frame, `GET /discharge`, and
the run summary (`--summary`). See
`scenarios/discharge-auto-order.json` for a runnable example:
over a seeded 40-tick run every order is placed the tick its bed
flags ready and every discharged patient leaves 5 s after
flagging, so the timing reports 2 measured orders (bed 3's
cancelled order is not measured — it never discharged), a mean
ready-to-order time of 0.0 s, and a mean and max
ready-to-discharge time of 5.0 s.

## Per-auto-order lead-time override

Auto orders normally use the planner's default lead time, but a
ward that sends a ready patient home quickly can override it for
auto orders only, with `auto_order_lead_time_s` in the
`discharge_readiness` block:

```json
{
  "discharge_planning": {"lead_time_s": 3600},
  "discharge_readiness": {
    "auto_order": true,
    "auto_order_lead_time_s": 600,
    "stable_window_s": 300
  }
}
```

The override applies only to orders the ward raises itself when a
bed is flagged discharge-ready. Scheduled orders still use the
planner's default (or their own per-order `lead_time_s`), and
manual orders placed live with `place_order` take whatever lead
time they are given. The discharge summary's orders already carry
each order's `expected_t`, so the override is visible there; the
readiness summary carries the override in force
(`auto_order_lead_time_s`, null when unset) in every snapshot,
WebSocket frame, `GET /discharge-readiness`, and the run summary
(`--summary`). See `scenarios/discharge-auto-order-lead-time.json`
for a runnable example: over a seeded 40-tick run with a 5-second
window, a 5-second planner default, and a 2-second override, beds
0 and 3 are quiet from admission and auto-discharge at 7 s, bed
1's dose lands at 30 s and it auto-discharges at 32 s, and bed 2
(missed insulin) never flags ready and gets no order — 3 auto
orders, 3 discharges, a mean ready-to-discharge time of 2.0 s.

## Auto orders in NEWS2 priority order

When several beds flag discharge-ready on the same tick, the ward
raises their auto orders in the discharge-priority order — safest
first, by NEWS2 at the flip that made each bed ready, lowest
first, ties by earliest flip then bed — instead of bed order.
The order the orders are raised in is the order they are listed
in the discharge summary, and the order they come due in, so
when cleaning is scarce the safest patient is first in line for
a cleaning slot: with one slot and three beds due at the same
time, the safest discharges on time and the others queue behind
it. The ordering only applies within a tick — a bed that flags
ready later still gets its order later, however safe it is — and
it only applies to orders the ward raises itself: scheduled and
manual orders keep the order they were placed in. A queued
discharge that is waiting for a cleaning slot also starts
cleaning in discharge-priority order — lowest NEWS2 at the flip
that made the bed ready first, ties by earliest flip then bed —
not in expected-time order, so among patients delayed by the
same backlog the safest patient gets the next slot even when
their discharge was due later; a bed that never flagged ready
has no NEWS2 at a flip and waits behind every ready bed, in
expected-time then bed order. The queue is visible in the
discharge summary (`cleaning_queue`, in start order) and the run
summary (`--summary`). See
`scenarios/discharge-auto-order-priority.json` for a runnable
example: over a seeded 40-tick run with a 5-second window, a
5-second lead time, and one cleaning slot, beds 0, 1, and 2 all
flag ready at 5 s — bed 1 at NEWS2 0, bed 0 at NEWS2 3 (stable
vitals, responds only to voice), bed 2 at NEWS2 4 (tachycardic)
— so the orders are raised 1, 0, 2, bed 1 discharges at 10 s
with no delay, bed 0 at 20 s, and bed 2 at 30 s, 30 s of delay
in total. See `scenarios/discharge-cleaning-priority.json` for
the queued case: over a seeded 40-tick run with one cleaning
slot, bed 0 discharges at 5 s and cleans until 15 s, bed 1
(tachycardic, NEWS2 2 at its flip) is due at 10 s and bed 2
(stable, NEWS2 0) at 12 s, so both queue — but bed 2 takes the
slot freed at 15 s and leaves 3 s late, while bed 1 waits until
25 s, 15 s late, 18 s of delay in total.

## Discharge-readiness hooks

A readiness flip says a patient just became ready to leave — or
just stopped being ready, because an alarm restarted their
stability clock; the hook makes sure something outside the ward
hears about it. A ward that wants the outside world to hear about
that moment — a bed manager, a dashboard, a discharge coordinator
— configures discharge-readiness hooks, the same channels as the
NEWS2 hooks (webhook and/or in-process callback), on the same
best-effort, never-fatal terms:

```json
{"discharge_readiness_hooks": {"webhook_url": "http://127.0.0.1:18099/hooks"}}
```

The hook fires once per flip, in the tick the flag changes, with
a `readiness_flip` event payload: the bed, the new state
(`"ready"` true or false), when it flipped, how long the vitals
have been stable, whether the medication orders are complete, and
the NEWS2 score at the flip — so the outside world can see what
the early-warning score said when the patient became ready (a
febrile patient can flag ready while still medium risk on NEWS2,
because readiness is judged on quiet vitals and complete orders,
not on the score). A bed that stays ready for an hour fires once,
not once a tick; a discharge ends the stay silently, so the next
patient in the bed starts from not-ready and their first flip is
a real one. Each flip event records whether the hook was invoked
(`"hook_invoked"`, False with no hooks) and any synchronous error
(`"hook_errors"`), and the readiness summary carries the flip
totals (`"readiness_flips"`, `"flips_to_ready"`,
`"flips_to_not_ready"`) and the ward discharge-readiness-hook
totals (`"discharge_readiness_hooks"`: whether any hook is
configured, how many deliveries were invoked, how many failed,
how many retries were spent, and how many deliveries eventually
landed) — in `GET /discharge-readiness`, every snapshot and
WebSocket frame, and the run summary (`--summary`). The same
retry rules as the NEWS2 hooks apply — a failed webhook POST is
retried with backoff up to `"max_retries"` times, and the event
records `"hook_retries"` and `"hook_final_status"` alongside
`"hook_invoked"`. Hooks are off by default, so a ward with none
configured behaves exactly as before. See
`scenarios/discharge-readiness-hooks.json` for a runnable example:
over a seeded 40-tick run the same ward as `discharge-ready.json`
flips 5 times — beds 0 and 3 ready at 5 s, bed 3 not ready at 8 s,
bed 1 ready at 30 s, bed 3 ready again at 39 s — POSTed to the
configured webhook, with 5 hook deliveries invoked and 0 failed
against a stub server.

## NEWS2 discharge priority

A ward with several patients flagged discharge-ready still has to
decide who goes home first. The discharge-priority view ranks the
ready beds by NEWS2, lowest first, so the safest patient to send
home is at the top: each entry carries the bed, the NEWS2 score at
the flip that made it ready (`"news2_at_flip"`, with the risk at
the flip), the current NEWS2 score (`"news2"`), when the bed
flagged ready (`"ready_t"`), and how long it has been ready
(`"time_ready_s"`). The ranking uses the score at the flip — the
stable, recorded value — not the score drifting tick by tick, and
ties break by the earliest flip, then bed number. Beds that are
not ready do not appear at all, and a bed drops out of the list
the moment it stops being ready.

This view ranks; it does not gate. Readiness is judged on quiet
vitals and complete orders, not on the score, so a patient can
flag ready at NEWS2 6 — and the priority view still lists them,
ranked last, not excluded: the score orders the queue, it never
decides who is in it. The view is served by
`GET /discharge-priority` (503 while partitioned), carried in
every snapshot and WebSocket frame, and the run summary
(`--summary`) reports the same order from the last tick. See
`scenarios/discharge-priority.json` for a runnable example: over
a seeded 60-tick run with a 5-second window, bed 0 (stable)
flags ready at 5 s at NEWS2 1, bed 1 (tachycardic) at 5 s at
NEWS2 3, and bed 2 (hypoxic) at 59 s at NEWS2 6, while bed 3
(febrile) never flags ready — the priority order is beds 0, 1,
2, ready 55 s, 55 s, and 1 s respectively.

## Discharge-priority hooks

The priority order is a queue a bed manager works through, so
when it changes — a bed becomes ready, a ready bed leaves, or
the ranking reorders — the hook makes sure something outside
the ward hears about it. A ward that wants the outside world to
hear about that moment — a bed manager, a dashboard, a discharge
coordinator — configures discharge-priority hooks, the same
channels as the NEWS2 hooks (webhook and/or in-process
callback), on the same best-effort, never-fatal terms:

```json

```

The hook fires once per order change, in the tick the order
changes, with a `discharge_priority_changed` event payload: the
new ordered bed list — the same entries `GET /discharge-priority`
serves, each with the NEWS2 at the flip, the current score, when
the bed flagged ready, and how long it has been ready — and the
order it replaces (`"previous_beds"`). A tick where the order is
unchanged fires nothing: a bed that stays ready for an hour sends
one notification, not one a tick. Each change event records
whether the hook was invoked (`"hook_invoked"`, False with no
hooks) and any synchronous error (`"hook_errors"`), and the
priority summary carries the change totals
(`"priority_changes"`, the full `"changes"` history) and the ward
discharge-priority-hook totals
(`"discharge_priority_hooks"`: whether any hook is configured,
how many deliveries were invoked, how many failed, how many
retries were spent, and how many deliveries eventually landed)
— in `GET /discharge-priority`, every snapshot and WebSocket
frame, and the run summary (`--summary`). The same retry rules
as the NEWS2 hooks apply — a failed webhook POST is retried with
backoff up to `"max_retries"` times, and the event records
`"hook_retries"` and `"hook_final_status"` alongside
`"hook_invoked"`. Hooks are off by default, so a ward with none
configured behaves exactly as before. See
`scenarios/discharge-priority-hooks.json` for a runnable example:
over a seeded 60-tick run the same ward as
`discharge-priority.json` changes its order 7 times — beds 0, 1
and 3 flag ready at 5 s, bed 3 drops out at 8 s, flags ready
again at 39 s and slots in ahead of bed 1 on NEWS2, bed 2 joins
at 49 s and drops out at 50 s, bed 3 drops out at 51 s, and bed 2
flags ready again at 59 s — POSTed to the configured webhook,
with 7 hook deliveries invoked and 0 failed against a stub
server.

## Discharge-priority history

The priority view says where each ready bed sits now; the
history says how it got there. Every time the ranked order
changes, each bed whose rank moved records one history entry:
the tick it changed, its new 1-based rank — null when it drops
out of the order — and the NEWS2 at the flip that had made it
ready, so a bed that leaves keeps the score it left with. A bed
whose rank did not change records nothing, so a ward that stays
ready for an hour records one entry per bed, not one per tick.
The history is grouped per bed (`"rank_history"`, keyed by bed
number) alongside the total count of rank changes
(`"rank_changes"`), in `GET /discharge-priority`, every snapshot
and WebSocket frame, and the run summary (`--summary`). See
`scenarios/discharge-priority-history.json` for a runnable
example: over a seeded 40-tick run all four beds flag ready at
5 s in the order 2, 3, 0, 1, an alarm storm on bed 0 at 10 s
drops it out of the order at 11 s and promotes bed 1 from rank
4 to 3, and bed 0 flags ready again at 20 s at NEWS2 0 and
retakes rank 3 while bed 1 falls back to 4 — 3 order changes,
8 rank changes in total.

## NEWS2 early-warning scoring

Every reading carries a NEWS2 score — the Royal College of
Physicians' National Early Warning Score 2 — computed from that
tick's vitals:

```json
{"news2": {"score": 6, "risk": "medium", "red_score": true,
 "spo2_scale": 1,
 "components": {"resp_rate": 2, "spo2": 3, "systolic": 0,
 "heart_rate": 1, "temperature": 0, "consciousness": 0},
 "response": "urgent review by ward team (hourly monitoring)"}}
```

Each of the six scored parameters contributes 0 to 3 points on
the standard NEWS2 bands (respiratory rate, SpO2, systolic blood
pressure, heart rate, temperature, consciousness). SpO2 is scored on Scale 1 for
patients not on oxygen and on Scale 2 for patients on oxygen (see
Oxygen therapy below). Consciousness is scored on the ACVPU scale
(see below): Alert scores 0, anything else scores 3. The aggregate drives the risk: 0-4 low, 5-6
medium, 7 or more high — and any single parameter scoring 3 is a
red score, which makes the risk medium even when the aggregate is
low. The response is NEWS2's own: routine monitoring at low risk,
urgent review by the ward team at medium, urgent review by the
critical care team at high.

Consciousness can change over a run when a patient has
`consciousness_dynamics` set (see Consciousness below): the level
steps one ACVPU level at a time, driven by how long the patient's
vitals-only NEWS2 risk holds, and every change is recorded with
its time in the early-warning summary. The score is
advisory only — a test signal for health software, not a clinical
judgement.

A patient whose risk leaves low opens a deterioration episode:
it records when it raised, the worst score it reached, and the
worst risk, and it closes when the risk returns to low (or when
the patient is discharged). Every snapshot carries an
`"early_warning"` object with the per-bed scores, whether an
episode is open, the episode history, and ward totals (beds at
each risk level, open episodes, episodes raised), served on its
own by `GET /news2` and carried in every WebSocket frame, and
the run summary (`--summary`) reports the same totals from the
last tick. The score never touches the alarm list: a hypoxic
patient's alarms are exactly the ones their vitals raise, so
alarm counts, alarm rates, and discharge readiness are
unchanged. See `scenarios/news2.json` for a runnable example:
over a seeded 40-tick run the stable bed scores 0 and never
escalates, the hypoxic bed sits at medium risk on a red SpO2
score and stays escalated from 1 s, the tachycardic bed stays
low, and the febrile bed deteriorates on its own (a medium
episode at 5-9 s) and then goes high under the alarm storm at
10 s, peaking at 11 and clearing at 40 s — 3 episodes raised in
total.

## Oxygen therapy and NEWS2 Scale 2

A patient can be on supplemental oxygen, set per patient in the
scenario:

```json
{"bed": 1, "profile": "hypoxic", "on_oxygen": true}
```

The flag is scoring only: it does not change the vitals the
monitor generates, so two wards with the same seed emit identical
signs and alarms whether or not a patient is on oxygen — only the
score differs. What changes is which SpO2 table NEWS2 uses. Scale 1
applies off oxygen (92-93 scores 2, 94-95 scores 1, 96 or above
scores 0); Scale 2 applies on oxygen, where the target band is
88-92, so 93-96 scores 2 and 97 or above scores 3 — the same SpO2
that is fine on air is a warning on oxygen, because a patient on
oxygen is expected to sit in the target band. Below the band the
tables agree in shape but not in edge: 88-92 scores 0 on Scale 2
and 3 on Scale 1, so a hypoxic patient at 89 is medium risk off
oxygen and low risk on it.

Every reading carries the flag (`"on_oxygen"`) and every score
carries which table was used (`"spo2_scale": 1` or `2`), so a
client can tell why two patients with the same SpO2 scored
differently. The early-warning summary carries the per-bed flag
and a ward count of patients on oxygen (`"on_oxygen"`). A new
admission starts off oxygen unless the admission says otherwise —
the previous patient's flag never carries over to the next patient
in the bed, and a triage admission is off oxygen by default.

One honest limitation: oxygen therapy is a flag, not a treatment
model. A real patient on oxygen would have their SpO2 lifted by
it; here the vitals keep whatever the profile produces, so a
hypoxic patient on oxygen can sit below the target band and a
stable one above it. The score is still NEWS2's own for the SpO2
the monitor shows — it just does not model the therapy working.
See `scenarios/oxygen.json` for a runnable example: over a seeded
40-tick run the stable patient on oxygen drifts above the target
band and escalates twice, the hypoxic patient on oxygen sits
inside 88-92 and never escalates, and the same hypoxic patient
off oxygen stays escalated from 1 s — 3 episodes raised in total,
2 patients on oxygen.

## Consciousness (ACVPU) and NEWS2

A patient can have a consciousness level on the ACVPU scale, set
per patient in the scenario:

```json
{"bed": 1, "profile": "stable", "consciousness": "voice"}
```

The levels are `alert`, `confusion`, `voice`, `pain`, and
`unresponsive` — Alert, Confusion, responding to Voice,
responding to Pain, Unresponsive. NEWS2 scores Alert 0 and
anything else 3, so a non-Alert patient is medium risk on the
consciousness red score alone, whatever their vitals say: a
stable patient who responds only to voice sits at medium risk
from the first tick, and a confused hypoxic patient is high,
because the two red scores stack.

Every reading carries the level (`"consciousness"`) and every
score carries its component (`"consciousness": 0` or `3`), so a
client can tell why two patients with the same vitals scored
differently. The early-warning summary carries the per-bed level
and a ward count of patients who are not Alert
(`"not_alert"`), and the run summary (`--summary`) reports the
same count. A new admission starts Alert unless the admission
says otherwise — the previous patient's level never carries over
to the next patient in the bed, and a triage admission is Alert
by default.

See `scenarios/news2-acvpu.json` for a runnable example of fixed
levels: over a seeded 40-tick run the Alert stable bed scores 0
and never escalates, the stable bed responding only to voice sits
at medium on the consciousness red score and stays escalated from
1 s, the confused hypoxic bed is high from 1 s peaking at 9,
and the unresponsive febrile bed is high from 1 s peaking at 9
— 3 episodes raised in total, 3 patients not Alert.

## Consciousness dynamics (ACVPU changing over a run)

By default the level is fixed, as above. A patient with
`consciousness_dynamics` in the scenario changes over time,
driven by their own vitals:

```json
{"bed": 1, "profile": "hypoxic",
 "consciousness_dynamics": {"deteriorate_after_s": 3, "recover_after_s": 3}}
```

The rule is a clock on the vitals-only NEWS2 risk — the score
with consciousness held at Alert, so the level itself cannot
drive the decision (a non-Alert patient is medium risk on the
consciousness red score alone, so judging by the total risk
would make recovery impossible). While the vitals risk is medium
or high the deterioration clock runs; while it is low the
recovery clock runs; a clock reaching its threshold steps the
level one ACVPU level in that direction and restarts, so a
patient slides from Alert toward Unresponsive one level at a
time while their vitals stay bad and climbs back one level at a
time as they recover, never jumping straight from Alert to
Unresponsive. `true` in place of the object means the defaults
(`deteriorate_after_s` 5, `recover_after_s` 10). The thresholds
must be numbers above 0; anything else is a scenario error.

Every change is recorded with its time (`"consciousness_history"`
per bed, `{"from", "to", "t"}`) and counted in the early-warning
summary (`"consciousness_changes"`, ward total and per bed), so a
client can see a patient who deteriorated and came back, not just
where they are now — and because the change is scored in the same
tick it happens, a dropping level raises the score, opens or
extends a deterioration episode, and shows up in the snapshot,
`GET /news2`, and every WebSocket frame at once. The dynamics are
deterministic and use no randomness, so a seeded run reproduces
the same changes, and enabling them never changes the vitals or
alarms a monitor generates. A new admission resets the level to
Alert and clears the history; the dynamics config is the bed's
scenario setting and still applies to the next patient.

One honest limitation: the model is a clock on the vitals, not a
cause. It does not distinguish why responsiveness changed — a
hypoxic slide, a sedative, a stroke all look the same one-step
clock — and the thresholds are a test-load choice, not a clinical
one. The score is still NEWS2's own for the level the monitor
shows; it just does not model the medicine behind the change.
See `scenarios/news2-acvpu-dynamics.json` for a runnable example:
over a seeded 40-tick run the Alert stable bed never changes, the
hypoxic bed slides Alert to Unresponsive at 3 s intervals (4
changes, high from 1 s peaking at 9), the febrile bed responding
only to voice recovers to Alert by 6 s and its first episode
closes there, and the confused stable bed recovers to Alert at
3 s — 7 changes and 5 episodes raised in total, 1 patient not
Alert at the end.

## NEWS2 score history

`GET /news2` says where each patient is now; `GET /news2/history`
says how they got there. Every fresh reading appends one entry to
its bed's history — the time, the score, the risk, the red-score
flag, the SpO2 scale, the per-parameter components, and the
consciousness level at that tick — so a client can plot a
patient's score over the run, or find when they crossed from low
to medium, without replaying a recording. The history is per stay:
a new admission clears it, and after a discharge the departed
patient's history stays, marked unadmitted, until the next
admission. It is capped at 1000 entries per bed, oldest first out;
the run summary still counts every tick scored. A stale tick
repeats the previous reading, so it records nothing — one entry
per reading, never a duplicate.

Each bed's entry carries the history list, the number of points,
the peak score and the risk at that score, and the latest entry as
`"current"`. `GET /news2/history?bed=2` returns one bed; the
whole-ward form returns every bed. The run summary carries the
same shape in aggregate per bed: ticks scored, peak score and
risk, ticks at each risk level, and the first and last scored
times. See `scenarios/news2-history.json` for a runnable example:
over a seeded 40-tick run the stable bed stays low (peak 1), the
hypoxic bed sits medium and drifts to high at the end (peak 7),
and the febrile bed peaks at 11 under the alarm storm and is low
again by the end — 10 high ticks, 17 low, the arc visible in the
history rather than just the final score.

## NEWS2 trend alerts

A score says how sick a patient looks; the trend says how fast
they are getting there. Every bed's history is watched for a
rising score, and a rise raises a trend alert — an episode, like
a deterioration episode, with raised and cleared times — in the
early-warning summary (`GET /news2`), in the history endpoint
(`GET /news2/history`), in every snapshot and WebSocket frame,
and in the run summary (`--summary`), which reports how many
trend alerts are open and how many have raised. Two rules, either
of which raises one:

- **jump** — the score rose by at least `delta` (2 by default)
  from the earliest entry inside the trailing `window_s`
  seconds (60 by default): a patient who deteriorates fast.
- **creep** — over the last `trend_ticks` entries (10 by default)
  the score rose on more ticks than it fell and the net rise is
  at least `min_rise` (2 by default): a patient who drifts up
  slowly, a point a tick, without ever jumping. A one-point
  wobble does not count as a trend.

Each bed's history entry carries the current trend — whether the
score is rising, which rule fired, the score the rise started
from and when (`"start_score"`, `"start_t"`), the current score,
and the rise (`"delta"`) — and each alert records when it raised
and cleared, the score it started from, the worst score it
reached, the biggest rise, and the rule. An alert closes when the
score stops rising: the window slides forward and the rise out of
it shrinks, or the recent ticks stop climbing — or when the
patient is discharged. Like the score itself, a trend alert never
touches the vital-sign alarm list: a hypoxic patient's alarms are
exactly the ones their vitals raise. The thresholds are set per
ward in the scenario:

```json
{"news2_trend": {"window_s": 10, "delta": 2}}
```

See `scenarios/news2-trend.json` for a runnable example: over a
seeded 40-tick run with a 10-second window the stable bed never
rises two points and raises nothing, the hypoxic bed drifts up
twice — a creep alert at 12-18 s and a jump alert from 35 s that

alert under the alarm storm, from 5 at 1 s to 11, a rise of 6,
clearing at 15 s when the storm ends — 3 trend alerts raised in
total, 1 still open.

## NEWS2 trend alert hooks

A trend alert is only useful if something outside the ward hears
about it. A scenario can configure hooks that fire when a trend
alert raises:

```json
{"trend_alert_hooks": {"webhook_url": "http://127.0.0.1:18099/hooks"}}
```

Two channels, either or both:

- **webhook** — the alert payload is POSTed as JSON to the URL:
  the bed, the rule that fired, when it raised, the score the rise
  started from and when, the peak score and rise so far. The POST
  runs in a daemon thread, so a slow or dead endpoint never blocks
  the ward tick — best effort, a failure is logged and counted,
  never fatal.
- **callback** — an in-process Python callable, called with the
  alert payload in the tick that raises the alert (Python API only
  — a scenario file cannot hold a callable). A callback that raises
  is caught, logged, and counted as a failure; the tick still
  completes.

Hooks are off by default: a ward with none configured behaves
exactly as before. A fired alert records whether the hook was
invoked (`"hook_invoked"` on the alert, False with no hooks) and
any synchronous error (`"hook_errors"`), so the alert carries the
delivery in the early-warning summary (`GET /news2`), the history
endpoint (`GET /news2/history`), every snapshot and WebSocket
frame, and the run summary (`--summary`). The early-warning
summary also carries the ward hook totals (`"trend_alert_hooks"`:
whether any hook is configured, how many deliveries were invoked,
how many failed, how many retries were spent, and how many
deliveries eventually landed).

A failed webhook POST is retried with exponential backoff: up to
`"max_retries"` retries (2 by default, so 3 attempts in total),
waiting `"retry_backoff_s"` seconds before the first retry (1.0
by default) and doubling after each failed attempt. A 2xx
response counts as delivered; a connection error, a timeout, or
any other status counts as a failed attempt. The retries run in
the same daemon thread as the first attempt, so a slow or dead
endpoint still never blocks the ward tick. Each alert records
how many retries its delivery took (`"hook_retries"`) and the
final outcome (`"hook_final_status"`: `"delivered"`,
`"failed"`, `"pending"` while a delivery is still in flight, or
`"not_invoked"` when no hook is configured) — the status is
updated when the delivery thread settles, so an alert read in
the very tick it raises may still say `"pending"`. A callback
that raises is not retried: a callback is in-process code, so a
failure there is a bug, not a transient network fault, and it
counts as failed at once.

```json
{"trend_alert_hooks": {"webhook_url": "http://127.0.0.1:18099/hooks",
                       "max_retries": 2, "retry_backoff_s": 0.5}}
```

One honest limitation: a webhook delivery is best effort, not
guaranteed. The ward records the final outcome once the retries
are spent, but nothing is persisted or re-queued across runs —
a delivery that gives up is gone, and a ward restarted mid-retry
loses the attempt. See `scenarios/news2-trend-hooks.json` for a
runnable example: over a seeded 40-tick run the same 3 trend
alerts raise as in `news2-trend.json`, each one POSTed to the
configured webhook, with 3 hook deliveries invoked and 0 failed
against a stub server. See
`scenarios/news2-trend-hooks-retry.json` for the retry half:
against a stub server that 500s twice before answering 200,
each of the 3 alerts lands on its third attempt — 9 POSTs, 6
retries, 3 delivered — and against the dead placeholder URL in
the file each alert takes 3 attempts and ends `"failed"` with
2 retries.

## NEWS2 escalation hooks

A trend alert says a patient is getting worse fast; an escalation
says they have already crossed into medium or high risk and need a
response. A ward that wants the outside world to hear about that
moment — a pager, a dashboard, a handover note — configures
escalation hooks, the same channels as the trend-alert hooks
(webhook and/or in-process callback), on the same
best-effort, never-fatal terms:

```json
{"escalation_hooks": {"webhook_url": "http://127.0.0.1:18099/hooks"}}
```

The hook fires once, in the tick the deterioration episode opens,
with an `escalation` event payload: the bed, when it raised, the
score and risk it raised at, the response NEWS2 calls for, and
when that response is due. The episode records whether the hook
was invoked (`"hook_invoked"`, False with no hooks) and any
synchronous error (`"hook_errors"`), and the early-warning
summary carries the ward escalation-hook totals
(`"escalation_hooks"`: whether any hook is configured, how many
deliveries were invoked, how many failed, how many retries were
spent, and how many deliveries eventually landed) — in `GET /news2`,
every snapshot and WebSocket frame, and the run summary
(`--summary`). The same retry rules as the trend-alert hooks
apply — a failed webhook POST is retried with backoff up to
`"max_retries"` times, and the episode records `"hook_retries"`
and `"hook_final_status"` alongside `"hook_invoked"`. Later ticks while the episode stays open fire
nothing: one escalation, one notification. Hooks are off by
default, so a ward with none configured behaves exactly as
before, and like every other NEWS2 feature they never touch the
vital-sign alarm list. See `scenarios/news2-escalation-hooks.json`
for a runnable example: over a seeded 40-tick run the hypoxic
bed escalates at 1 s and the febrile bed escalates at 1 s too,
before the alarm storm at 5 s pushes it to high — 2 escalations,
2 hook deliveries invoked and 0 failed against a stub server.

## NEWS2 response timing

An escalation says a patient needs a response; the response
timing says how long the ward took to give one. Every
deterioration episode records the response NEWS2 calls for at
the risk it raised at — urgent review by the ward team for
medium, urgent review by the critical care team for high — when
that response was due, when it landed, and how long it took
from the escalation raising to the first response action.
The response is due 30 seconds after the escalation raises with
an adequate roster, times the staffing load factor at the moment
it raised — the same clock as an alarm acknowledgement — so a
ward with one nurse for twelve beds responds in 90 seconds and
a ward with no nurse on shift in 120, and a handover stretches
it further, exactly like an alarm ack. The response lands at
its scheduled time, even when that is the very tick the risk
returns to low — the team was already on its way. An episode
that closes before its response is due keeps both times null:
it cleared before anyone responded, and that is worth knowing
too — a discharge closes an episode the same way.

The early-warning summary (`GET /news2`, every snapshot and
WebSocket frame) aggregates the timing across the ward: how many
escalations got a response, how many closed before anyone
responded, how many are still waiting, and the mean and longest
time from an escalation raising to the response landing (null
before the first response). The run summary (`--summary`)
reports the same totals from the last tick.

One honest limitation: the response is a scheduled arrival, not
a modelled intervention. It does not change the patient's vitals
or score — the team arrives, the patient is still as sick as
the monitor says — and it pauses while the monitor is offline
or the reading is stale, because no fresh reading means no
escalation to respond to, just as an offline monitor's alarms
are neither raised nor cleared. Like the score itself, the
response never touches the vital-sign alarm list. See
`scenarios/news2-response.json` for a runnable example: over a
seeded 40-tick run the hypoxic bed's escalation gets its
response 30.0 s after it raises, the febrile bed's brief medium
episode at 5-9 s clears before its response is due at 35 s and
stays unresponded, and its high episode under the storm gets
its response at 40 s, the very tick the risk returns to low —
2 responded, 1 unresponded, a mean and max of 30.0 s.

## NEWS2-driven staffing escalation

An escalation says a patient needs a response; a ward full of
high-risk patients says the roster itself needs help. When the
number of deterioration episodes open at high NEWS2 risk
reaches a threshold, the ward calls in extra nurses — the
effective roster grows, so the load factor falls and alarms are
acknowledged faster, vitals checks run on time again, and
escalation responses are due sooner, because all three clocks
run on the load factor. The escalation is hysteresis, not a
switch: once active it holds while the count stays at or above
the threshold, and after the count drops below it the extra
nurses stay for a cooldown before standing down, so a ward
hovering at the threshold does not flap staff in and out every
tick.

```json
{"news2_staffing_escalation": {"threshold_high": 2, "extra_nurses": 1, "cooldown_s": 60}}
```

`threshold_high` is how many open high-risk episodes trigger
an escalation (2 by default), `extra_nurses` is how many
additional nurses join the effective roster while one is active
(1 by default), and `cooldown_s` is how long the escalation
holds after the count drops below the threshold (60 seconds by
default). The staffing summary (`GET /staffing`, every snapshot
and WebSocket frame) carries the escalation state — whether one
is configured and active, the threshold and extra nurses in
force, how many high-risk episodes are open, and every
escalation raised so far, with when it raised and cleared, how
many high episodes were open when it raised and at their worst,
and which beds they were — and the run summary (`--summary`)
reports the same totals from the last tick. Each open high
episode is flagged as covered (`"staffing_escalated"` on the
episode in `GET /news2`), so a client can see which patients
the extra staff were called in for. The rostered staff in the
summary stay the roster (`"on_shift"`), and
`"escalation_nurses"` says how many extra nurses are on the
effective roster — the ratio and the load factor count both.
Off by default, so a ward with no config behaves exactly as
before, and like every other NEWS2 feature the escalation never
touches the vital-sign alarm list or the scores themselves — it
only changes how fast the ward responds to them. See
`scenarios/news2-staffing-escalation.json` for a runnable
example: over a seeded 40-tick run on a thin night (one nurse
for eight beds, a load factor of 2.0) two febrile beds go high
under an alarm storm at 5 s, the ward calls in one extra nurse
at 5 s and the load factor falls to 1.0 — 9 of 14 alarms
acknowledged by 40 s at a mean of 30.0 s, against 0
acknowledged without the escalation — and the escalation is
still active at the end, the 60 s cooldown holding it past the
storm until 95 s.

## Recording a run

`--record FILE` writes every tick to a JSONL file: a header line with
the run's beds, rate, and seed, then one line per tick holding the
snapshot exactly as the ward emitted it. Plain JSONL, so any tool can
read a recording without this package.

```sh
python3 -m ward.cli --summary run.jsonl   # ticks, duration, readings/offline/stale per bed, alarms raised
python3 -m ward.cli --replay run.jsonl    # the recorded ticks, one JSON object per line
```

The summary counts an alarm once, when it first appears in a bed's
reading — the same raise/clear transitions the monitor records. A
recording with a partition in it still records every tick; the
endpoints returned 503 while it lasted, the ticks did not stop.

## Roadmap

- Patient acuity model (acuity 1-4 driving vitals volatility and
  alarm rates) — done in v0.6.0
- Staffing/shift model (nurse-to-patient ratios affecting alarm
  response times) — done in v0.7.0
- Bed turnover (discharges and new admissions refilling beds) — done
  in v0.8.0
- Medication administration (scheduled doses, staffing-driven late
  and missed doses with missed-dose alarms, interaction warnings) —
  done in v0.9.0
