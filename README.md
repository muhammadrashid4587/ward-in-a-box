# ward-in-a-box

A simulated hospital ward as a load and chaos generator for health software.

## What it is

A pure Python 3 (stdlib only) simulator of a small ward — 12 beds by
default, each with a virtual monitor emitting vitals (heart rate, SpO2,
blood pressure, temperature, respiratory rate) at a configurable rate.
A chaos engine injects the failures real ward software has to survive:
device dropout, alarm storms, stale readings, and network partitions
between the ward and the server. An HTTP endpoint streams the vitals as
JSON lines so real health software can be tested against it, and a small
CLI runs a scenario file.

## What it is not

This is **not medical software**. It does not monitor real patients, it
does not diagnose or treat anything, and it must never be used in a
clinical setting. Every reading is synthetic, generated by a random
walk inside plausible ranges. It is a test tool for software, nothing
more.

## Quickstart

```sh
# Run the example scenario (12 beds, chaos starts at 30s)
python3 -m ward.cli scenarios/example.json

# Admissions ramp-up: 4 beds over 10s, then 8 by 50s, then all 12 by 70s
python3 -m ward.cli scenarios/ramp-up.json

# Ad-hoc ward: 6 beds at 2 Hz on port 9000
python3 -m ward.cli --beds 6 --rate 2 --port 9000

# Print one snapshot and exit
python3 -m ward.cli --beds 4 --once

# Record a run to a file, then summarise it (or replay its ticks)
python3 -m ward.cli scenarios/example.json --seed 42 --record run.jsonl
python3 -m ward.cli --summary run.jsonl
python3 -m ward.cli --replay run.jsonl

# Staffing demo: full day roster, one nurse on nights from 19:00
python3 -m ward.cli scenarios/staffing.json --seed 42

# Bed turnover: beds 1 and 2 discharge, clean for 10s, then refill
python3 -m ward.cli scenarios/turnover.json --seed 42

# Medication: interaction warnings up front, insulin missed on thin nights
python3 -m ward.cli scenarios/meds.json --seed 42

# Reproducible run
python3 -m ward.cli scenarios/example.json --seed 42
```

## Endpoints

- `GET /health` — `{"status": "ok", "beds": 12}`
- `GET /snapshot` — the latest reading for every bed as JSON,
  plus a `"staffing"` object (see below)
- `GET /stream` — the ward ticking live, one JSON object per line
- `GET /ws` — WebSocket endpoint streaming one JSON message per tick
  (beds plus alarm and staffing summaries; see below)
- `GET /alarms` — per-bed alarm history and rate metrics as JSON
  (503 while partitioned)
- `GET /staffing` — the current shift, roster on duty, nurse-to-patient
  ratio, alarm acknowledgement and vitals-check metrics as JSON
  (503 while partitioned)
- `GET /turnover` — per-bed turnover state (`occupied`, `cleaning`,
  `available`), turnovers and total cleaning time per bed, plus ward
  totals, as JSON (503 while partitioned)
- `GET /meds` — per-bed medication schedules, interaction warnings,
  and given/late/missed dose counts, plus ward totals, as JSON
  (503 while partitioned)

A reading looks like:

```json
{"bed": 2, "seq": 31, "t": 30.0, "profile": "tachycardic", "acuity": 2,
 "heart_rate": 108.4, "spo2": 96.2, "systolic": 128.0,
 "diastolic": 82.0, "temperature": 36.9, "resp_rate": 17.5,
 "alarms": [], "stale": false, "online": true}
```

Offline beds appear as `{"bed": 2, "online": false, "t": 30.0}`.
Beds not yet admitted by a scenario timeline appear the same way,
with an extra `"admitted": false`. While a partition is active,
`/snapshot` and `/stream` return 503.

## WebSocket endpoint

`GET /ws` with a standard WebSocket upgrade (`Upgrade: websocket`,
`Sec-WebSocket-Key`) returns `101 Switching Protocols` and then
streams one JSON text frame per tick at the ward rate:

```json
{"t": 30.0, "beds": [...], "alarms": {"t": 30.0, "beds": [...], "total_raised": 3, "rate_per_min": 1.2}, "staffing": {"t": 30.0, "shift": "day", "on_shift": {"nurse": 3, "doctor": 1, "tech": 1}, "patients_per_nurse": 4.0, "adequate": true, "alarms": {"raised": 3, "acked": 3, "pending": 0, "mean_time_to_ack_s": 30.0}, "checks": {"performed": 12, "delayed": 0}}}
```

Each frame carries the same snapshot as `/snapshot` plus the alarm
summary from `/alarms`, the staffing summary from `/staffing`, and the
medication summary from `/meds`, so a client gets bed occupancy,
vitals, alarms, staffing, and medication in one message. Ping frames are answered with pong, close frames
are echoed and the connection is then closed; text frames from the
client are accepted and ignored — the ward pushes ticks, it takes no
input. While a partition is active the upgrade is refused with 503,
like the other live endpoints. Pure stdlib: the framing is a minimal
hand-rolled RFC 6455 implementation in `ward/websocket.py`.

## Alarm history and rates

Every time a bed's vitals cross out of (or back into) a normal band, the
monitor records an alarm event:

```json
{"alarm": "tachycardia", "raised_t": 31.0, "cleared_t": 47.0}
```

`GET /alarms` returns, per bed, the alarms currently active, the full
history (capped at the last 1000 events per bed; the total count keeps
counting past the cap), the total number of alarms raised, and the alarm
rate — alarms raised per minute over a trailing 60-second window. The
ward totals are the sums across beds. A stale reading repeats the
previous alarms, so it records nothing; while a monitor is offline its
alarms are neither raised nor cleared, and transitions are recorded
against the last reading it emitted when it comes back.

## Scenario format

```json
{
  "beds": 12,
  "rate_hz": 1.0,
  "host": "127.0.0.1",
  "port": 8080,
  "patients": [{"bed": 0, "profile": "stable"}],
  "chaos": [
    {"type": "dropout", "bed": 2, "at": 30, "duration": 10},
    {"type": "stale", "bed": 5, "at": 45, "duration": 15},
    {"type": "alarm_storm", "beds": [0, 1, 2], "at": 60, "duration": 20},
    {"type": "partition", "at": 90, "duration": 15}
  ]
}
```

Patient profiles: `stable`, `tachycardic`, `hypoxic`, `febrile`.
Beds without a named profile cycle through a default mix.

## Patient acuity

Each patient also has an acuity, 1 (critical) to 4 (low/stable), on a
triage-like scale, set per patient in the scenario:

```json
{"bed": 0, "profile": "tachycardic", "acuity": 1}
```

Acuity changes how a patient's vitals behave. A critical patient
swings twice as hard per tick and wanders 35% further from the
profile midpoint, so they cross alarm bands more often; a low-acuity
patient is steadier and stays closer to the middle. Level 3 is the
neutral default and reproduces exactly the old profile behaviour, so
scenarios that do not set acuity are unchanged. Acuity 2 sits in
between (1.5x volatility, 15% wider). The widened ranges are clamped
inside a plausible envelope, so no acuity level can push a vital
somewhere a real monitor would never show. The reading and the
`/alarms` summary both carry the bed's acuity, so a client can tell a
quiet stable patient from a quiet critical one. See
`scenarios/acuity.json` for a ward with one patient at each level: over
a seeded 600-tick run the acuity-1 hypoxic patient raised 61 alarms
against 16 for the acuity-4 one.

Chaos types:

- `dropout` — a monitor goes offline for `duration` seconds; its bed
  stops appearing in the stream.
- `stale` — a monitor freezes on its last reading (flagged `"stale": true`).
- `alarm_storm` — vitals on the target beds are dragged out of their
  normal bands, so every bed raises alarms.
- `partition` — the ward is cut off from the server; endpoints return 503.
- `discharge` — the target beds' patients are discharged at `at`
  (instant, so `duration` is ignored and may be omitted); see
  Bed turnover below.

`bed` targets one bed, `beds` targets several, neither targets all beds
(`partition` is always ward-wide). Times are elapsed seconds from start.

## Staffing and shifts

The ward runs on two shifts — day 07:00–19:00, night 19:00–07:00 —
each with its own roster of nurses, doctors, and techs, set in the
scenario:

```json
{"staffing": {
  "start_hour": 18,
  "day": {"nurse": 3, "doctor": 1, "tech": 1},
  "night": {"nurse": 1, "doctor": 1, "tech": 0}
}}
```

The ward clock starts at `start_hour` (08:00 by default, an hour into
the day shift). What matters for care is the nurse-to-patient ratio:
one nurse keeps up with up to four occupied beds. Past that, alarms
take longer to acknowledge and routine vitals checks slip later, in
proportion to the overload. The first fifteen minutes after a shift
change are a handover, when response is half as fast again even with
a full roster. The model is deterministic: with an adequate roster an
alarm is acknowledged 30 seconds after it is raised and a vitals
check is due every 60 seconds; a ward with one nurse for twelve beds
acknowledges in 90 seconds and its checks run every 180 seconds, so
they count as delayed. `GET /staffing` (and every snapshot and
WebSocket frame) reports the shift, the roster on duty, the ratio,
whether it is adequate, the current load factor, alarms raised/acked/
pending with mean time-to-ack, and checks performed/delayed. See
`scenarios/staffing.json` for a ward that is fine on days and thin on
nights: over a seeded 400-tick alarm storm the full roster
acknowledged in 30.0 s on average with 0 delayed checks, against
90.0 s and 24 delayed checks with one nurse.

## Scenario timelines (admissions with ramp-up)

A scenario can add a `timeline` of admission phases. The ward starts
empty and beds come online as the timeline admits them — useful for
testing how health software handles a ward filling up, rather than a
ward that is full from the first second.

```json
{
  "beds": 12,
  "timeline": [
    {"at": 0, "beds": 4, "ramp_s": 10},
    {"at": 30, "beds": 8, "ramp_s": 20},
    {"at": 60, "beds": 12, "ramp_s": 10}
  ]
}
```

Each phase names a target number of occupied beds and a time to reach
it: starting at `at`, beds are admitted one by one over `ramp_s`
seconds until `beds` beds are occupied (`ramp_s` 0 admits them all at
once, at `at`). Between phases the occupancy stays at the last target.
Targets only go up — this is admissions, not discharges — and a phase
may not target more beds than the ward has. Beds keep the profiles
from the scenario's `patients` list (or the default mix) when they are
admitted. See `scenarios/ramp-up.json` for a runnable example.

## Bed turnover

When a patient is discharged, the bed is not free at once: it goes
through cleaning first. A bed has three states — `occupied` while a
patient is admitted, `cleaning` after a discharge until turnover
finishes, `available` once it can take a new admission. The cleaning
duration is `cleaning_s` seconds, set on the ward (30 by default) or
in the scenario:

```json
{
  "beds": 4,
  "cleaning_s": 10,
  "timeline": [{"at": 0, "beds": 4, "ramp_s": 0}],
  "chaos": [
    {"type": "discharge", "bed": 1, "at": 5},
    {"type": "discharge", "bed": 2, "at": 8}
  ]
}
```

A discharged bed stops emitting readings and cannot be re-admitted
until its cleaning time has elapsed — an admission attempt while
cleaning raises an error. A scenario timeline does not pull a bed out
of cleaning either: it refills the bed on the first tick after
turnover finishes, so a discharge followed by a refill tests exactly
the gap a real ward has. A new admission starts with fresh vitals, so
the previous patient's readings and alarms do not carry over, and a
discharge clears the patient's active alarms.

Every snapshot carries a `"turnover"` object with the per-bed state,
when a cleaning bed becomes available, how many turnovers each bed
has had, and the total cleaning time per bed, plus ward totals
(`occupied`, `cleaning`, `available`, `total_turnovers`,
`total_cleaning_s`). The same summary is served by `GET /turnover`.
Offline beds in a snapshot also carry their state (`"cleaning"` or
`"available"`). See `scenarios/turnover.json` for a runnable example:
bed 1 discharges at 5 s and is refilled at 15 s, bed 2 discharges at
8 s and is refilled at 18 s.

## Medication administration

Each patient can have scheduled medications, set per patient in the
scenario:

```json
{"bed": 0, "profile": "stable",
 "meds": [{"name": "metoprolol", "every_s": 3600,
           "first_at": 0, "grace_s": 600}]}
```

A dose due at `t` is administered 30 seconds later with a full
roster, slowed by the same staffing load factor that slows alarm
acknowledgement — so a thin night shift delays medication too. A dose
given more than 300 seconds after it was due counts as late; a dose
whose administration would land past `due + grace_s` (600 seconds by
default) is missed instead, and the miss raises a `missed_dose` alarm
on the bed until that medication's next dose is given. A discharge
clears the patient's medication state, and a new admission starts
with a fresh schedule.

Some medication pairs interact. A small table of known pairs
(warfarin + aspirin, metoprolol + verapamil, insulin + metoprolol,
lisinopril + spironolactone, digoxin + furosemide) produces warnings
in the medication summary — warnings only, the doses still happen,
because a simulator should surface the risk, not decide the
prescription.

Every snapshot carries a `"meds"` object with the per-bed schedules,
warnings, given/late/missed counts, and ward totals. The same
summary is served by `GET /meds`. See `scenarios/meds.json` for a
runnable example: bed 0 is on warfarin and aspirin, bed 1 on
time-critical insulin with a 60-second grace window, bed 3 on
lisinopril and spironolactone. Over a seeded 7200-tick run the day
shift gives every dose, the night shift (one nurse for twelve beds)
misses the insulin dose, and 2 interaction warnings are raised.

## Recording a run

`--record FILE` writes every tick to a JSONL file: a header line with
the run's beds, rate, and seed, then one line per tick holding the
snapshot exactly as the ward emitted it. Plain JSONL, so any tool can
read a recording without this package.

```sh
python3 -m ward.cli --summary run.jsonl   # ticks, duration, readings/offline/stale per bed, alarms raised
python3 -m ward.cli --replay run.jsonl    # the recorded ticks, one JSON object per line
```

The summary counts an alarm once, when it first appears in a bed's
reading — the same raise/clear transitions the monitor records. A
recording with a partition in it still records every tick; the
endpoints returned 503 while it lasted, the ticks did not stop.

```sh
make test
```

96 tests: vitals stay inside plausible ranges, dropout actually stops a
monitor's stream, an alarm storm produces alarms, stale readings freeze,
a partition blocks the snapshot endpoint, the HTTP endpoints serve valid
JSON, the stream serves JSON lines, scenario files validate, alarm
history records raises and clears, alarm rate counts a trailing window,
the ward summary aggregates per-bed alarms, and `/alarms` serves JSON
(503 while partitioned). Timeline tests cover linear ramp-up, instant
phases, per-bed admission times, decreasing-target and bad-value
rejection, beds coming online as the timeline admits them, a timeline
target above the bed count, and the `ramp-up.json` scenario loading and
filling the ward. WebSocket tests cover the RFC 6455 accept key and
frame round-trip, the 101 handshake, tick frames carrying beds and
alarms, ping/pong, the close handshake, fragmented client messages, a
400 without upgrade headers, and a 503 while partitioned. Recording
tests cover the header and tick lines, the summary's tick, duration,
reading, offline, and alarm counts, an empty recording, tick replay,
and the `--record`, `--summary`, and `--replay` CLI flags. Acuity tests
cover range widening and narrowing by level, the plausible envelope,
rejection of bad acuity values, the default of 3, readings and alarm
summaries carrying acuity, a critical patient swinging and alarming
more than a low-acuity one, ward-level acuities, and the `acuity.json`
scenario loading with per-bed acuities. Staffing tests cover day/night
shift boundaries, roster counts per shift, the fifteen-minute handover
window, the load factor at 1:4, 1:6, and 1:12 ratios and during
handover, zero nurses on shift, rejection of bad rosters, a seeded
alarm storm proving one nurse for twelve beds triples mean time-to-ack
(90.0 s vs 30.0 s) and delays vitals checks (24 delayed vs 0),
staffing in snapshots and ward summaries, the `/staffing` endpoint
(503 while partitioned), and the `staffing.json` scenario loading with
per-shift rosters. Turnover tests cover discharge moving a bed to
cleaning and stopping its readings, a discharged bed refusing
re-admission until turnover finishes and then taking a new patient
with fresh vitals, per-bed turnover counts and total cleaning time,
discharge/admit rejection on the wrong state, a timeline not pulling
a bed out of cleaning and refilling it after, the `discharge` chaos
event firing exactly once, the `/turnover` endpoint (503 while
partitioned), and the `turnover.json` scenario discharging two beds
and refilling both after cleaning. Medication tests cover validation
of schedule values and duplicate names, a dose given on time with an
adequate roster, a dose going late when one nurse covers 64 beds
(480.0 s delay), a dose missed when the delay exceeds its grace
window and the missed-dose alarm clearing on the next given dose, a
missed dose raising a `missed_dose` alarm in the bed's reading, the
`/meds` endpoint (503 while partitioned), a discharge resetting the
medication state, interaction warnings for warfarin + aspirin and
lisinopril + spironolactone, and the `meds.json` scenario giving 7
doses and missing 1 over a seeded run.
